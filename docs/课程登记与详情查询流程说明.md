# 课程登记与课程详情查询流程说明

> 本说明只依据当前仓库中实际存在的源码、公开文档与测试编写，范围限定为：**课程标题、有序章节、本地保存**这条路径（登记课程 → 取得课程编号 → 查询同一课程详情）。
> 每条结论均给出可定位的源码位置；文档与代码不一致处分别记录、不代为裁决。文中的命令与输出均已在本机用当前源码实跑核对（Python 3.14.4，SQLite 标准库）。

## 1. 公开入口总览

调用形式（`README.md:7`，`course_progress/__main__.py:22-50`）：

```bash
python -m course_progress --db <数据库文件> <子命令> ...
```

`build_parser()` 中实际只注册了三个子命令（`__main__.py:28-50`）：

- `add-course`：登记课程（`__main__.py:30-38`）。`--title` 必填；`--chapter` 使用 `action="append"`，可重复，**参数出现的先后顺序被保留**。
- `get-course <course_id>`：按编号查询详情（`__main__.py:40-42`）。
- `list-courses`：查询全部课程概览（`__main__.py:44-49`）。本路径中它可作为"已知有哪些编号"的辅助手段（见 §4.2）。

`--db` 在全局参数和每个子命令上各注册了一次、目标属性同名（`__main__.py:27、31、41、47-48`），因此写在子命令前或后都能解析（README 承诺，测试 `tests/test_cli_flow.py:110-127` 覆盖）。

除上述三个子命令外，包内不存在课程修改、删除、学员、练习、结业等任何命令或模块（证据范围：`__main__.py:28-50` 的子命令注册表 + 包文件清单）。这些功能在本仓库中为**未实现**，本文档不展开。

## 2. 存储位置的选择方式与表结构

### 2.1 存储位置完全由每次调用的 `--db` 决定，没有默认值

- `main()` 取 `getattr(args, "db", None)`；未提供时直接向标准错误打印 `必须通过 --db 指定数据库文件` 并返回退出码 `2`，不会打开任何数据库（`__main__.py:64-67`）。
- 代码中不存在环境变量、配置文件或默认路径。相对路径按调用进程的当前工作目录解析（标准 `sqlite3.connect` 行为）。
- 不同 `--db` 文件互相独立（`README.md:71`）。

### 2.2 打开即建库建表

`connect(db_path)`（`core.py:29-33`）依次执行：

1. `sqlite3.connect(db_path)`：文件不存在时自动创建（`README.md:7`）；**父目录必须已存在**，否则抛出 `sqlite3.Error`，`main()` 捕获后向标准错误打印 `无法打开数据库：{exc}`、退出码 `1`（`__main__.py:69-72`）。实测父目录缺失时消息为 `无法打开数据库：unable to open database file`。
2. `executescript(_SCHEMA)`：确保两张业务表存在。

实际表定义（`core.py:11-22`，并已通过读取磁盘库文件核对一致）：

```sql
CREATE TABLE IF NOT EXISTS courses (
    id INTEGER PRIMARY KEY AUTOINCREMENT,   -- 课程编号，数据库生成
    title TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS chapters (
    course_id INTEGER NOT NULL REFERENCES courses (id),
    position INTEGER NOT NULL,              -- 章节序号，0 起，登记顺序
    name TEXT NOT NULL,
    PRIMARY KEY (course_id, position)
);
```

字段与关联要点：

- **课程编号** = `courses.id`，`INTEGER PRIMARY KEY AUTOINCREMENT`，由 SQLite 在插入时生成，不由用户指定。全新数据库首个编号为 1，之后递增（README:22；回归断言 `tests/test_cli_flow.py:78、99`；磁盘上可见 SQLite 自动维护的 `sqlite_sequence` 表）。
- **课程与章节的关联** = `chapters.course_id` 外键指向 `courses.id`；章节本身没有独立编号，主键是 `(course_id, position)`，即同一课程内位置唯一。
- `courses.title` 上**没有**唯一约束，代码中也没有同标题检查，即相同标题的课程可以重复登记（文档侧佐证：`README.md:50` "同标题的课程分别列出"）。

## 3. 一次登记请求：从输入到结果

命令分支：`main()` → `add_course(conn, args.title, args.chapter)`（`__main__.py:74-81`）。

### 3.1 接收与规范化（保存之前）

在 `add_course()`（`core.py:36-57`）中，先做字符串规范化，再做校验，最后才开事务写库：

1. `title = title.strip()`；章节名逐个 `name.strip()`（`core.py:42-43`）。**首尾空白在保存前被去除**，查询取回的也是去除后的值（测试 `tests/test_cli_flow.py:94-108`）。
2. 校验按固定顺序进行，只可能抛出第一个错误（`core.py:44-49`；顺序承诺见 `README.md:62`，测试 `tests/test_cli_flow.py:175-194`）：
   1. 去空白后标题为空 → 抛 `ValidationError(ERR_EMPTY_TITLE)`（`课程标题不能为空`）；
   2. 章节列表为空，或任一章名去空白后为空 → 抛 `ValidationError(ERR_EMPTY_CHAPTER)`（`章节不能为空`）；
   3. 去空白后章节名有重复（`len(set(names)) != len(names)`，Python 字符串比较，**大小写敏感**）→ 抛 `ValidationError(ERR_DUP_CHAPTER)`（`章节名重复`）。
3. 以上全部通过后才进入写入事务。

注意：这里没有对课程标题做查重，也没有章节数量上限、字符集等其他检查——源码中不存在对应代码。

### 3.2 写入与关联（同一事务）

`add_course()` 在校验通过后打开事务（`core.py:50-56`）：

1. `INSERT INTO courses (title) VALUES (?)`，从 `cursor.lastrowid` 取出生成的课程编号 `course_id`（`core.py:51-52`）。
2. `executemany` 批量插入章节，`position` 来自 `enumerate(names)`，即 **0、1、2……** 与 `--chapter` 的出现顺序一一对应（`core.py:53-56`）。这是课程与章节的唯一关联动作。
3. 离开 `with conn:` 块时提交；课程行与章节行在同一事务内，要么同时生效要么都不生效。

此外整个命令体外层还有一层 `with conn:`（`__main__.py:73`）；校验失败时异常在执行任何 INSERT 之前就已抛出（见 §6）。

### 3.3 结果输出

成功：标准输出一行 JSON `{"course_id": <编号>}`，退出码 `0`（`__main__.py:80`，`json.dumps(..., ensure_ascii=False)`，中文不转义）。
失败：`ValidationError` 在 `main()` 中被捕获，错误消息写入**标准错误**，返回退出码 `1`，此时**标准输出为空**（`__main__.py:77-79`；测试断言 `tests/test_cli_flow.py:63-66`）。

### 3.4 课程编号怎样取得

- **登记结果本身即编号**：`add-course` 标准输出的 JSON 字段 `course_id` 就是后续查询所需编号（§5 示例演示"不预设编号、从登记结果取用"）。
- 辅助方式：`list-courses` 返回所有课程的 `course_id`、`title`、`chapter_count`，按编号升序，但**不含章节名**（`core.py:60-78`，`README.md:38-50`）。

## 4. 查询同一课程：章节顺序由什么决定

### 4.1 get-course 流程

1. 编号合法性在 CLI 层解析：`parse_positive_int()`（`__main__.py:53-59`）先 `strip()`，再用正则 `_ID_PATTERN = re.compile(r"[+-]?\d+")` 做 `fullmatch`，`int()` 转换后要求 `> 0`；不满足返回 `None` → 标准错误 `课程编号必须为正整数`、退出码 `2`（`__main__.py:89-92`，常量 `ERR_BAD_ID` 见 `core.py:9`）。
2. 调用 `get_course(conn, course_id)`（`core.py:81-95`）：
   - 先 `SELECT title FROM courses WHERE id = ?`；查不到返回 `None` → CLI 打印 `课程不存在`、退出码 `1`（`__main__.py:93-96`）。
   - 再 `SELECT name FROM chapters WHERE course_id = ? ORDER BY position`（`core.py:88-94`）。
3. 成功输出：`{"course_id": <编号>, "title": <标题>, "chapters": [<名称序列>]}`，退出码 `0`（`core.py:95`、`__main__.py:97-98`）。

**章节顺序的决定因素是 `chapters.position` 列**（登记时按 `--chapter` 出现顺序写入的 0 起序号），查询以 `ORDER BY position` 显式排序，而不是依赖插入先后或名称排序。输出中不暴露 `position`，只暴露按其排好序的名称数组。

### 4.2 list-courses（辅助）

SQL 为 `courses LEFT JOIN chapters` 后 `GROUP BY c.id ORDER BY c.id`，章节数来自 `COUNT(ch.position)`（`core.py:66-78`）。空库时该命令也会触发建库建表，并返回 `{"courses": []}`、退出码 `0`（`README.md:50`，测试 `tests/test_cli_flow.py:70-73`）。

## 5. 固定示例：标题"入门培训"，章节"准备 / 学习 / 回顾"

以下命令形式与 README 公开入口完全一致，输出为当前源码实跑结果。

### 5.1 准备：确保父目录存在

```bash
mkdir -p data
```

（`--db` 的父目录不会被自动创建，见 §2.2。）

### 5.2 登记（输入）

```bash
python -m course_progress --db data/course.db add-course \
    --title "入门培训" \
    --chapter "准备" --chapter "学习" --chapter "回顾"
```

### 5.3 取得课程编号（不预设具体编号）

标准输出为一行 JSON（在全新数据库上实跑为下方结果）：

```json
{"course_id": 1}
```

退出码 `0`。后续查询应**解析登记输出中的 `course_id` 字段**取得编号，而不是假设它等于某个固定值（仅"全新库的第一门课"恰为 1，依据 §2.2 的 AUTOINCREMENT 与测试 `tests/test_cli_flow.py:78`）。也可用 `list-courses` 对照编号与标题。

### 5.4 查询详情（用上一步取得的编号，此处为 1）

```bash
python -m course_progress --db data/course.db get-course 1
```

实跑返回（单行 JSON）：

```json
{"course_id": 1, "title": "入门培训", "chapters": ["准备", "学习", "回顾"]}
```

退出码 `0`。可确认的返回内容：`course_id=1`、标题与输入一致（本例无首尾空白）、`chapters` 三个元素，顺序为 **准备 → 学习 → 回顾**，由 `position` 0、1、2 与 `ORDER BY position` 决定（§4.1）。直接读取磁盘库文件可见对应行：`courses (1, '入门培训')`；`chapters (1,0,'准备')、(1,1,'学习')、(1,2,'回顾')`。

### 5.5 关闭程序后重新打开同一存储位置

再次以**同一个 `--db data/course.db`** 调用 `get-course 1`（新进程），返回与 §5.4 完全相同。这是 SQLite 文件落盘的直接结果；测试中以两个独立子进程完成同样验证（`tests/test_cli_flow.py:94-108`，用例名 `test_add_then_get_preserves_order_across_processes`）。换用另一个 `--db` 文件则看不到该课程。

## 6. 三类失败的检查位置、可观察结果与数据残留

| 情形 | 检查位置 | 标准错误（实测） | 退出码 | 标准输出 | 是否留下课程数据 |
| --- | --- | --- | --- | --- | --- |
| 空标题（去首尾空白后为空，如 `--title "   "`） | `core.py:44-45`（先于一切 INSERT） | `课程标题不能为空` | `1`（`__main__.py:77-79`） | 空 | **不留下任何数据行** |
| 同一课程内重复章节名（去空白后、大小写敏感比较，如 `--chapter " 学习 " --chapter "学习"`） | `core.py:48-49` | `章节名重复` | `1` | 空 | **不留下任何数据行** |
| 未知课程编号（正整数但库中不存在，如 `get-course 42`） | `core.py:83-87` 返回 `None`，CLI `__main__.py:93-96` | `课程不存在` | `1` | 空 | 查询只读，本就不写入 |
| 编号不是正整数（`0`、`-3`、`abc`） | `__main__.py:53-59、89-92` | `课程编号必须为正整数` | `2` | 空 | 同上，不写入 |

补充实测：

- **失败后无残留的依据有两层**：三类登记校验全部位于 `add_course()` 开启写入事务之前（`core.py:44-49` 在 `core.py:50` 之前），异常路径不执行任何 INSERT；异常又穿过 `main()` 的 `with conn:`（`__main__.py:73-79`）。实跑中先制造空标题、重复章节两次失败，再 `list-courses`，结果只剩此前登记的课程 1，数量为 3 章，没有新增课程。
- 空标题实跑命令：`add-course --title "   " --chapter "准备"`；重复章节实跑命令：`add-course --title "其他课" --chapter " 学习 " --chapter "学习"`；未知编号实跑命令：`get-course 42`。
- 相关测试：空标题 `tests/test_cli_flow.py:130-140`、无章节 `142-145`、空章节名 `147-159`、重复 `161-172`、错误优先级 `175-194`、未知正整数编号 `198-200`、编号 `0` `202-204`。每个用例随后用空库/重新登记证明失败未写入（`assert_empty_db_then_register`，`tests/test_cli_flow.py:68-90`）。
- **但需注意文件层面的副作用（措辞边界，见 §7 记录 B）**：若 `--db` 指向一个尚不存在的文件，即使登记校验失败，`connect()` 已在校验前创建了数据库文件与表。

## 7. 公开文档与代码的对照记录（分别记录，不代为裁决）

**记录 A：前导 `+` 的编号，文档未列举，代码有确定行为。**

- 文档内容：`README.md:69` 称"编号不是正整数（如 `0`、`-3`、`abc`）"时输出 `课程编号必须为正整数`、退出码 `2`，未提及 `+3`。
- 代码/实测内容：正则为 `[+-]?\d+`（`__main__.py:19`），`parse_positive_int` 接受前导 `+`（`__main__.py:53-59`）。实测 `get-course +3` 被当作编号 3；在课程 3 不存在时输出 `课程不存在`、退出码 `1`，而非退出码 `2`。
- 两侧原文如上，是否属于"正整数"由读者判断；另：测试只覆盖了 `0`（`tests/test_cli_flow.py:202-204`），`-3`、`abc`、`+3` 无对应用例，本文结论来自源码与手动实跑。

**记录 B：失败后"不留下任何记录"的措辞边界。**

- 文档内容：`README.md:54` "……数据库不留下任何记录"。
- 代码/实测内容：`connect()` 在 `add_course()` 校验**之前**执行建库建表（调用顺序 `__main__.py:69 → 76`，实现 `core.py:29-33`）。实测对全新路径执行一次空标题失败登记后，磁盘上已存在该 db 文件，且含 `courses`、`chapters`、`sqlite_sequence` 三张表，但 `courses`/`chapters` 数据行数均为 0。
- 即"无业务数据行残留"成立；"不产生文件/表"不成立。本文按此精确措辞描述（§6）。

**记录 C：argparse 层失败不在文档中文失败表内。**

- 文档内容：`README.md:52-69` 的失败结果表只覆盖业务校验与编号校验。
- 代码/实测内容：缺少必填的 `--title`、使用未知子命令等情形由 argparse 直接处理，输出**英文** usage/error（如 `error: the following arguments are required: --title`），退出码 `2`（实测）。文档未记载该输出形态。

**记录 D：文档未记载但代码确实存在的输入行为。**

- `--db` 同时在全局与子命令后给出时，因目标属性同名，argparse 以**最后一次出现**为准（实测子命令后的 `--db` 覆盖前者；定义点 `__main__.py:27、31、41`）。
- `get-course` 的编号参数在匹配前先 `strip()`（`__main__.py:55`），实测 `" 1 "` 会按编号 1 正常查询；README 未提及首尾空白被容忍。

## 8. 持久化结论小结

1. 保存位置：每次调用由 `--db` 显式指定的 SQLite 文件，无默认值、无其他存储后端（§2）。
2. 落盘内容：`courses`（生成的整数编号 + 去空白标题）与 `chapters`（所属课程编号、0 起位置、去空白章节名），同一事务提交（§3.2）。
3. 重开取回：进程退出后，用同一 `--db` 路径在新进程中 `get-course <编号>` 可取回原标题与按登记顺序排列的章节（§5.5，测试 `tests/test_cli_flow.py:94-108`）。
4. 失败原子性：登记校验失败不产生任何业务数据行（§6）；仅可能在全新路径上留下已建好空表的数据库文件（§7 记录 B）。
