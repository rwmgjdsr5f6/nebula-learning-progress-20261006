## 2. 调用形式与 `--db` 语义

命令语法（`__main__.py:164-174`）：

```
python -m course_progress [--db <文件>] list-course-learners <course_id> [--name-contains <片段>] [--db <文件>]
```

- `course_id` 为必填位置参数，语义为「课程编号（正整数）」（`__main__.py:170`）。
- `--name-contains` 为**可选参数**：省略时列出该课程全部已报名学员（见第 6.1 节）；
  显式给出时按姓名片段筛选（见第 5 节）。注意「省略」与「显式给出空字符串」
  是两条不同路径，后者是失败情形（见第 7 节）。
- 每次用 `--db` 指定 SQLite 数据库文件，**父目录必须预先存在**；文件不存在时
  自动创建并建表（`README.md:7`；`core.py:116-120`）。
- `--db` 写在子命令前后语义相同：全局 `--db` 定义于 `__main__.py:49`，子命令级
  `--db` 定义于 `__main__.py:167-169`（`default=argparse.SUPPRESS`），两者汇入
  同一个 `args.db`，由 `main` 在 `__main__.py:227-230` 统一读取；不提供 `--db`
  时标准错误为 `必须通过 --db 指定数据库文件`，退出码 2，不接触数据库。

## 3. 端到端路径总览：命令行输入如何变成 JSON

```
命令行参数
  └─ argparse 解析（build_parser）                     __main__.py:164-174
       │    缺少位置参数 course_id 时由 argparse 拒绝：英文 usage 错误
       │    写 stderr，stdout 为空，退出码 2；此时尚未 connect，不创建数据库文件
       └─ 读取 --db（子命令前后同义）                    __main__.py:227
            └─ connect(db_path)：打开/创建 SQLite 并建表  core.py:116-120
                 │    （先于编号解析与一切业务校验，见第 8.3 节）
                 └─ parse_positive_int(args.course_id)   __main__.py:283
                      │    非法（如 0、abc）→ stderr 课程编号必须为正整数，退出码 2
                      │         （__main__.py:284-286，消息常量 core.py:13）
                      └─ list_course_learners(conn, course_id, name_contains)
                                                           core.py:615-660
                           ├─ ① 编号范围检查（超出 int64 按不存在）
                           │      core.py:630-631
                           ├─ ② 课程存在性检查 SELECT 1 FROM courses
                           │      core.py:632-636，不存在 → 返回 None
                           │        → stderr 课程不存在，退出码 1
                           │          （__main__.py:294-296，消息常量 core.py:12）
                           ├─ ③ 筛选词规整（仅当显式给出 --name-contains）
                           │      strip() 去首尾空白；为空 → ValidationError
                           │      core.py:637-640
                           │        → stderr 学员姓名筛选词不能为空，退出码 1
                           │          （__main__.py:287-293，消息常量 core.py:15）
                           ├─ ④ 报名范围读取：enrollments JOIN learners
                           │      WHERE e.course_id = ? ORDER BY l.id
                           │      core.py:641-654
                           └─ ⑤ 姓名片段匹配：name_contains in learner["name"]
                                  大小写敏感连续子串，Python 侧过滤
                                  core.py:655-659
                 └─ stdout 输出一行 JSON                 __main__.py:297-302
                      {"course_id": N, "learners": [...]}，退出码 0
```

六个环节依次为：**编号解析**（CLI 层）→ **课程判定**（core 层先查编号范围、
再查课程存在性，以返回值 `None` 表达不存在）→ **筛选词规整**（课程存在之后才
进行）→ **报名范围限定**（SQL 的 `WHERE e.course_id = ?` 内连接）→ **姓名片段
匹配**（Python 侧子串过滤）→ **命令行输出**（CLI 层封装单行 JSON）。

错误优先级即前三个判定环节的先后顺序，详见第 7 节。

## 5. 筛选词的处理与匹配规则

### 5.1 只去首尾空白，保留内部空白

规整只执行一次 `name_contains.strip()`（`core.py:637-638`）：首尾空白（空格、
制表符、换行等）被去除，**内部空白原样保留并参与匹配**。因此 `" Ann "` 与
`Ann` 等价，而 `"An n"`（中间一个空格）、`"An  n"`（中间两个空格）是不同的
筛选词。回归测试 `test_internal_whitespace_is_preserved_in_filter`
（`tests/test_list_course_learners_name_filter.py:224-249`）先把学员 1 改名为
`An n`，再验证 `"  An n  "` 命中（首尾空白被去掉）而 `"An  n"` 无匹配
（内部双空格不存在于姓名中）；函数层对应用例在第 432–439 行。

### 5.2 对当前姓名做大小写敏感的连续子串匹配

匹配表达式是 Python 的 `name_contains in learner["name"]`（`core.py:655-659`），
即对数据库中**当前保存的完整姓名**做连续子串匹配，区分大小写，不做分词、不做
正则、不做大小写折叠。每次查询实时读取 `learners.name`（SQL 在
`core.py:643-644`），不保存报名时或上次查询的姓名快照，因此改名后按新姓名
匹配（见第 8.1 节）。

### 5.3 百分号、下划线、引号都是普通字符

匹配在 Python 侧用 `in` 完成（`core.py:655-659`），**不是 SQL `LIKE`**，筛选词
从不作为模式传入 SQL，因此 `%`、`_` 没有通配含义，引号也没有表达式含义，
一律按普通字符做字面子串匹配。回归测试
`test_percent_underscore_quote_are_literal_characters`
（`tests/test_list_course_learners_name_filter.py:190-222`）把学员 1 改名为
`A%_"n` 后验证：`%` 只字面命中含百分号的学员 1、不匹配学员 2，`_`、双引号 `"`
以及组合片段 `%_"` 均按字面命中同一人；函数层对应用例在第 416–430 行。

### 5.4 匹配范围只限该课程的已报名学员

候选名单由第 ④ 步的 SQL 一次性限定（`core.py:641-650`）：

```sql
SELECT l.id, l.name
FROM enrollments AS e
JOIN learners AS l ON l.id = e.learner_id
WHERE e.course_id = ?
ORDER BY l.id
```

- `WHERE e.course_id = ?` 绑定目标课程编号（`core.py:646,649`），**其他课程的
  报名行不可能进入候选**；
- `enrollments JOIN learners` 是内连接：只列出在该课程有报名行的学员，**未报名
  该课程的学员（包括只报名了其他课程的学员 3，以及从未报名任何课程的学员）
  不会混入**；
- 片段匹配（第 ⑤ 步）只在这个候选名单内进行，不可能把范围外的人筛回来。

回归测试 `test_filter_only_applies_to_target_course_enrollments`
（`tests/test_list_course_learners_name_filter.py:168-188`）覆盖课程间隔离：
课程 2 筛 `Ann` 只得学员 3（不含同名的学员 1），课程 2 筛 `ann` 返回空数组
（学员 2 未报名课程 2）；函数层对应用例在第 411–414 行。

### 5.5 同名学员按编号区分

输出每项同时带 `learner_id` 与 `name`（`core.py:651-654`），排序与身份只认
编号（SQL 的 `ORDER BY l.id`，`core.py:647`），姓名从不作为唯一身份。样例中
学员 1 与学员 3 都叫 `Ann`，两人分别成项、互不合并：课程 1 的查询只能得到
学员 1，课程 2 的查询只能得到学员 3（第 4.2 节与第 5.4 节所引测试共同锁定）。
学员登记本身也允许同名分别建档（`add_learner`，`core.py:442-455`）。

## 6. 省略筛选词与空结果

### 6.1 省略 `--name-contains`：列出全部已报名学员，按编号升序

省略该参数时 argparse 不提供该属性，CLI 以 `getattr(args, "name_contains", None)`
传入 `None`（`__main__.py:288-290`）；`list_course_learners` 中 `name_contains
is None` 时跳过规整与过滤（`core.py:637,655`），直接返回第 ④ 步读出的全部
已报名学员，顺序由 SQL 的 `ORDER BY l.id` 保证（`core.py:647`）。对样例库执行：

```bash
python -m course_progress --db sample.db list-course-learners 1
```

预期标准输出（单行 JSON，学员 1 在前、学员 2 在后，与报名先后无关）：

```json
{"course_id": 1, "learners": [{"learner_id": 1, "name": "Ann"}, {"learner_id": 2, "name": "ann"}]}
```

退出码 0，标准错误为空。回归测试
`test_omitted_filter_returns_all_enrolled_sorted_by_id`
（`tests/test_list_course_learners_name_filter.py:149-166`）断言顺序与字段集合
（顶层仅 `course_id/learners`，每项仅 `learner_id/name`）；函数层
`test_none_and_omitted_return_all_enrolled_sorted`（同文件第 393–400 行）同时
覆盖省略参数与显式传 `None`。

### 6.2 无人报名与没有匹配项：成功返回空 `learners` 数组

两种情况都属于查询成功，退出码 0、标准错误为空，标准输出中 `learners` 为空
数组，二者代码根源不同：

| 情形 | 代码根源 | 预期输出 |
| --- | --- | --- |
| 课程存在但无人报名 | 内连接读不到任何报名行，列表本身为空（`core.py:641-654`） | `{"course_id": N, "learners": []}` |
| 有人报名但无姓名匹配 | 候选非空，Python 过滤后列表为空（`core.py:655-659`） | `{"course_id": N, "learners": []}` |

注意二者与「课程不存在」（空 stdout、退出码 1，见第 7 节）互斥。回归测试
`test_course_without_enrollments_returns_empty_roster`

## 7. 错误优先级与失败结果

三个判定环节严格按「编号格式 → 课程存在性 → 筛选词非空」的顺序短路，多个问题
同时存在时只报最先遇到的一个。所有失败均**标准输出为空、标准错误只有一行中文
消息、不出现异常堆栈**（CLI 分别以 `print(..., file=sys.stderr)` 配合显式
`return` 处理，`__main__.py:284-296`）。

| 优先级 | 输入情形 | 标准错误 | 退出码 | 代码位置 | 覆盖测试 |
| --- | --- | --- | --- | --- | --- |
| ① 编号格式 | `list-course-learners 0` | `课程编号必须为正整数` | **2** | `parse_positive_int` 返回 `None`（`__main__.py:283-286`；正则 `__main__.py:34`，`> 0` 判断 `__main__.py:198`）；消息常量 `core.py:13` | `test_non_positive_or_non_numeric_id_exits_2`（第 349–358 行，含 `0`、`-1`、`abc`） |
| ① 编号格式 | `list-course-learners abc` | `课程编号必须为正整数` | **2** | 同上（正则 `fullmatch` 失败，`__main__.py:195-196`） | 同上 |
| ② 课程不存在 | 正整数编号库中不存在，如 `999` | `课程不存在` | **1** | 存在性查询无行 → 返回 `None`（`core.py:632-636`）→ CLI 报错（`__main__.py:294-296`）；消息常量 `core.py:12` | `test_unknown_course_reports_not_found_even_with_empty_filter`（第 323–334 行） |
| ② 课程不存在 | `9223372036854775808`（2^63，超出 SQLite 64 位有符号整数上限） | `课程不存在` | **1** | 编号能通过正整数解析，但被 int64 范围检查拦下，按不存在处理（`core.py:630-631`，上下界常量 `core.py:47-48`），避免 `OverflowError` 外泄 | `test_overflow_course_id_reports_not_found`（第 336–347 行）；夹具常量在第 34 行 |

| ③ 筛选词为空 | 课程存在，`--name-contains "   \t "`（全为空白） | `学员姓名筛选词不能为空` | **1** | 同上，`strip()` 后为空字符串 | `test_whitespace_only_filter_exits_1_with_message`（第 312–321 行）；函数层第 459–466 行另含 `"\t\n  "` |

要点：

- **退出码 2 与 1 的分界**在编号格式：不是正整数（`0`、负数、非数字）一律 2；

- **「课程不存在」优先于「筛选词为空」**是源码顺序决定的：`list_course_learners`

- 上述每个失败用例都断言标准输出为空（`assertEqual(result.stdout, "")`）且

  筛选、空筛选词失败、课程不存在失败之后，快照比对四张业务表全部不变。

## 8. 改名、重开与建库建表边界

### 8.1 改名后按新姓名筛选

姓名匹配读取的是查询时刻的 `learners.name`（`core.py:643-644,655-659`），
`rename-learner` 只更新姓名、不改编号（`core.py:458-481`）。改名后下一次筛选：
新姓名命中，旧姓名不再命中；报名关系不受影响。回归测试
`test_rename_then_filter_matches_new_name`
（`tests/test_list_course_learners_name_filter.py:251-275`）把学员 1 改名为
`Beth` 后验证 `Beth` 命中、旧名 `Ann` 在课程 1 已无匹配（学员 2 是小写
`ann`）；函数层对应用例在第 441–448 行。

### 8.2 重开同一数据库结果一致

每条 CLI 命令都是独立进程，样例数据由登记/报名命令在各自事务中提交
（`core.py:137-143,452-454,550-559`），查询只读取文件；关闭后重新打开同一
`--db` 路径，省略筛选与带筛选的结果都与之前一致。函数层测试
`test_reopen_same_file_keeps_filter_results_consistent`
（`tests/test_list_course_learners_name_filter.py:490-499`）显式关闭连接后
重开同一文件，比对 `" Ann "` 与省略筛选两种结果；CLI 层全部用例本身就由
`register_sample` 写入后另起子进程查询（`run_cli`，同文件第 43–50 行），
跨进程一致性被每个用例反复覆盖。不同 `--db` 文件彼此独立（`README.md:201`）。

### 8.3 首次查询可能建库建表，但不产生业务记录

文件/表结构层面与业务记录层面是两件事：

1. **打开即可能创建文件与表**：`main` 在分派到任何子命令前先执行
   `connect(db_path)`（`__main__.py:232`，先于第 283 行的编号解析）。
   `connect` 中的 `sqlite3.connect` 在文件不存在时创建空文件，
   `executescript(_SCHEMA)` 再以 `CREATE TABLE IF NOT EXISTS` 建立
   `courses/chapters/learners/enrollments` 等表（`core.py:116-120`，DDL 在
   `core.py:19-39`）。因此对全新路径执行一次查询，即使该查询最终失败
   （课程不存在退出码 1，甚至编号为 `0` 退出码 2），也会留下一个已建表、
   业务表全为空的数据库文件。该现象在文档核对时于独立临时目录实跑确认：
   全新库执行 `list-course-learners 1 --name-contains "Ann"` 得到
   `课程不存在`、退出码 1，四张业务表行数均为 0；全新库执行
   `list-course-learners 0` 同样留下已建表文件并报
   `课程编号必须为正整数`、退出码 2。
2. **查询对业务记录零写入**：`list_course_learners` 全程只有 `SELECT`
   （`core.py:632-650`），没有 INSERT/UPDATE/DELETE；CLI 虽在
   `with conn:` 中分派（`__main__.py:236`），本分支无任何写入可提交。成功与
   失败查询后业务数据不变由第 7 节所引两个只读测试覆盖（快照比对四张表）。
3. 连文件都不会创建的失败只有 **argparse 阶段拒绝**：缺少位置参数时
   `parse_args` 在 `__main__.py:226` 直接退出（`connect` 尚未执行），
   英文 usage 错误写标准错误、退出码 2。
4. 父目录不存在属于打开失败：标准错误 `无法打开数据库：…`，退出码 1
   （`__main__.py:233-235` 捕获 `sqlite3.Error`）；第 4 节在已存在的空目录中
   准备样例，不触发该情形。

## 9. 核对结论

- 第 4.2、4.3 节两条验收输出（`" Ann "` 只返回学员 1、`"ann"` 只返回学员 2；
  退出码 0、标准错误为空、单行 JSON）分别对应 `core.py:637-659` 与
  `__main__.py:297-302`，由
  `tests/test_list_course_learners_name_filter.py:119-147` 逐字符锁定。
- 筛选词只去首尾空白、保留内部空白、对当前姓名做大小写敏感连续子串匹配，
  以及 `%`、`_`、引号为普通字符，根源是规整用一次 `strip()`
  （`core.py:638`）且匹配用 Python `in` 而非 SQL `LIKE`（`core.py:655-659`）；
  测试覆盖第 224–249、190–222 行。
- 其他课程与未报名学员不混入由内连接加 `WHERE e.course_id = ?` 保证
  （`core.py:641-650`，测试第 168–188 行）；同名学员按编号区分由
  `ORDER BY l.id` 与输出携带 `learner_id` 保证（`core.py:647,651-654`）。
- 省略筛选词返回全部已报名学员（按编号升序）走 `None` 分支

  与无匹配均成功返回空 `learners` 数组（`core.py:641-659`，测试第 277–300 行）。
- 错误优先级「编号格式（退出码 2）→ 课程存在性（退出码 1）→ 筛选词非空
  （退出码 1）」由 CLI 解析（`__main__.py:283-286`）与 core 内检查顺序
  （`core.py:630-640`）共同固定；`0`/`abc`、999、`9223372036854775808`、
  空筛选词及其优先组合均有测试（同文件第 302–358、468–476 行），失败时
  标准输出为空且无异常堆栈。
- 改名后按新姓名筛选（`core.py:458-481,643-644`，测试第 251–275 行）、重开
  同一库结果一致（测试第 490–499 行）、首次查询只建库建表而不改业务记录
