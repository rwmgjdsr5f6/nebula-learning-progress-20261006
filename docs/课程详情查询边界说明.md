## 2. 端到端流程总览（源码推导）

`python -m course_progress --db <文件> get-course <编号>` 一次调用的固定次序：

```
argv
 └─ argparse 解析（build_parser）                 __main__.py:26-90
     └─ 取 --db（getattr(args, "db", None)）      __main__.py:104
         ├─ 未提供：stderr「必须通过 --db 指定数据库文件」，退出码 2   __main__.py:105-107
         └─ connect(db_path)                      __main__.py:109
              ├─ sqlite3.connect(db_path) 打开/创建数据库文件   core.py:38
              ├─ executescript(_SCHEMA) 确保两张表存在          core.py:39,13-24
              └─ 失败（如父目录不存在）：stderr「无法打开数据库：…」，退出码 1  __main__.py:110-112
     └─ parse_positive_int(course_id)             __main__.py:129 → :93-99
         ├─ None：stderr「课程编号必须为正整数」，stdout 空，退出码 2     __main__.py:130-132
         └─ 正整数 n：get_course(conn, n)         __main__.py:179 → core.py:259-279
              ├─ 超出 int64 范围或 courses 无此行 → None
              │    stderr「课程不存在」，stdout 空，退出码 1             __main__.py:180-182
              └─ 命中：dict 三字段 → json.dumps(..., ensure_ascii=False)
                   stdout 一行 JSON，退出码 0                            __main__.py:183-184
```

两个次序要点（后文边界结论都依赖它们）：

1. **建库建表先于一切查询判定**：`connect()` 在 `__main__.py:109` 执行，编号解析在
   `:129`，课程查找更在 `core.py` 的 `get_course` 内。因此即使编号格式非法，
   数据库文件与表也已经创建（详见第 7 节）。
2. **范围守卫先于 SQL**：`get_course` 进入后首先判断编号是否落在 64 位有符号整数
   范围内，越界直接返回 `None`，不执行任何 SQL（`core.py:265-266`，详见第 6 节）。

## 3. 固定样例：Python 入门 / 安装环境 / 第一段程序

### 3.1 通过既有登记入口建立样例

前提：使用一个**全新的数据库文件**，其父目录已存在。在仓库根目录执行：

```bash
mkdir -p data
python -m course_progress --db data/course.db add-course \
    --title "Python 入门" \
    --chapter "安装环境" --chapter "第一段程序"
```

- 该命令是 README 已记载的登记入口（`README.md:11-14`），`--chapter` 按命令行出现
  顺序收集（`__main__.py:37-42`，`action="append"`，注释「出现顺序即章节顺序」）。
- 全新数据库得到编号 **1** 的依据（源码推导）：`courses.id` 为
  `INTEGER PRIMARY KEY AUTOINCREMENT`（`core.py:14-17`），新编号取自
  `cursor.lastrowid`（`core.py:58-59`），空库的首行序列号为 1；README 第 22 行同样
  记载「全新数据库的首个编号为 1」。
- **预期结果**（上述全新库前提成立时；退出码 0）：

  ```json
  {"course_id": 1}
  ```

- **实测**：本次核对在 `/tmp` 的独立空库上以等价命令
  （`python3 -m course_progress --db <临时目录>/data/course.db add-course ...`）
  实际执行，stdout 为 `{"course_id": 1}`，stderr 为空，退出码 0，与预期一致。
  仓库自带的 `data/course.db` 未执行该写命令。

### 3.2 查询命令与预期结果

```bash
python -m course_progress --db data/course.db get-course 1
```

**预期结果**：退出码 **0**，标准错误为空，标准输出为一行 JSON，内容为：

```json
{"course_id": 1, "title": "Python 入门", "chapters": ["安装环境", "第一段程序"]}
```

- 字段固定且仅为 `course_id`、`title`、`chapters` 三枚，由 `get_course` 返回的字典
  决定（`core.py:279`），CLI 以 `print(json.dumps(course, ensure_ascii=False))`
  输出（`__main__.py:183`）。本文不为查询引入任何新参数或新字段。
- 一处如实注明的字节细节：`json.dumps` 默认分隔符使实际输出在冒号与逗号后带一个
  空格，即实际字节形如
  `{"course_id": 1, "title": "Python 入门", "chapters": ["安装环境", "第一段程序"]}`；
  它与上面的紧凑写法是**同一个 JSON**（解析后内容完全一致，中文均不转义）。
  **实测**：临时独立库上执行该查询，stdout 即此带空格形式，stderr 为空，退出码 0。
- 标题中的内部空格（`Python 入门`）原样回显：查询路径不做任何空白裁剪或大小写
  变换，`get_course` 直接回传存储值（`core.py:267-279`）；首尾空白只在**登记**时
  被去除（`add_course` 的 `title.strip()` 与章节名 `strip()`，`core.py:49-50`），
  内部空白与大小写始终保留。

### 3.3 章节为什么按保存的位置读取

- **保存时每个章节带有显式位置**：`add_course` 在一个事务内用
  `enumerate(names)` 写入 `(course_id, position, name)`，位置从 **0** 起依次为
  0、1（`core.py:57-63`）。「安装环境」位置为 0，「第一段程序」位置为 1。
- **读取时按位置列排序**：章节列表来自
  `SELECT name FROM chapters WHERE course_id = ? ORDER BY position`
  （`core.py:272-278`）。因此顺序由 `chapters.position` 的**升序**决定——即登记时
  保存的位置——而不是章节名的字典序，也不是行在表中的物理顺序。
- 表结构也约束同一课程不占用重复位置：联合主键
  `PRIMARY KEY (course_id, position)`（`core.py:18-23`）。

### 3.4 程序退出后再次查询为何仍是相同顺序

- 登记在 `with conn:` 事务中提交到普通 SQLite 文件（`core.py:57-63`；
  `connect` 即 `sqlite3.connect(db_path)`，`core.py:36-40`），进程退出后数据已落盘。
- 再次执行 `get-course` 是对**同一个 `--db` 路径**重新打开同一个文件，重新跑同一条
  `ORDER BY position` 查询（`core.py:272-278`），位置未变，顺序必然一致；排序不依赖
  内存状态或插入后的偶然行序。
- **实测**：登记进程退出后另起多次 `get-course 1`，输出与第 3.2 节完全一致。
  仓库测试 `tests/test_cli_flow.py:94-108`
  （`test_add_then_get_preserves_order_across_processes`）亦以两个独立子进程
  覆盖跨进程顺序保持。
- **不同数据库彼此独立**（既有语义，README 第 95 行）：存储位置的唯一来源是
  `--db`（`__main__.py:104`，无默认路径、无环境变量）。**实测**：在另一个独立空库
  登记标题不同的课程同样得到编号 1，两个文件各自 `get-course 1` 只返回本库的课程，
  互不可见。

## 4. 编号解析规则（源码推导 + 实测）

唯一入口是 `parse_positive_int(raw)`（`__main__.py:93-99`），步骤固定：

1. `text = raw.strip()`——剥去**外围**空白（含空格、制表符等）；
2. 用 `_ID_PATTERN = re.compile(r"[+-]?\d+")` 对剥空白后的文本做 `fullmatch`
   （`__main__.py:23,96`）：整段必须是「可选的一个 `+`/`-` 号 + 一位以上数字」；
3. `int(text)`——Python 整数任意精度，此步对再长的数字串也**不会**抛
   `OverflowError`（异常只会出现在后续绑定到 SQLite 时，而第 6 节说明该路径已被
   范围守卫拦截）；
4. 仅当结果 `value > 0` 时接受，否则返回 `None`。

由此得到的边界（均已实测）：

| 输入 | 解析结果 | 后续可观察结果（在含样例课程的库上实测） |
| --- | --- | --- |
| `1` | 1 | 命中样例课程，退出码 0 |
| `" 1 "`、`"\t1 "` | 1（外围空白被剥去） | 与 `1` 相同，命中样例课程 |
| `001` | 1（前导零被 `int()` 消化） | 与 `1` 相同，命中样例课程 |
| `+1` | 1（正则允许可选正号） | 与 `1` 相同，命中样例课程 |
| `0`、`+0` | `None`（不大于 0） | stderr「课程编号必须为正整数」，退出码 2 |
| `-3` | `None`（负数） | stderr「课程编号必须为正整数」，退出码 2 |
| `abc` | `None`（fullmatch 失败） | stderr「课程编号必须为正整数」，退出码 2 |
| `1.5`、`0x1`、`1 2` | `None`（非纯整数形态） | stderr「课程编号必须为正整数」，退出码 2 |

注意区分两件事：**编号合法只表示通过了格式解析，并不表示课程存在**。`+1`、`001`、
`" 1 "` 合法且样例课程恰好存在，所以成功；而 `42` 同样是合法正整数，库中无此课程时
得到的是「课程不存在」（退出码 1），见第 5 节。

## 5. 确定的失败结果

以下结果对当前源码是确定的：消息只写到 stderr，stdout 为空，不出现异常堆栈。

### 5.1 编号不是正整数：退出码 2

| 输入 | 标准输出 | 标准错误 | 退出码 |
| --- | --- | --- | --- |
| `get-course 0` | 空 | `课程编号必须为正整数` | 2 |
| `get-course -3` | 空 | `课程编号必须为正整数` | 2 |
| `get-course abc` | 空 | `课程编号必须为正整数` | 2 |

依据：`parse_positive_int` 返回 `None` 后，`__main__.py:129-132` 打印常量
`ERR_BAD_ID`（`core.py:11`）并 `return 2`。**实测**三项与上表逐项一致。
测试覆盖：`tests/test_cli_flow.py:202-212`。

### 5.2 编号合法但课程不存在：退出码 1

| 输入 | 标准输出 | 标准错误 | 退出码 |
| --- | --- | --- | --- |
| `get-course 42`（未知正整数） | 空 | `课程不存在` | 1 |
| `get-course 9223372036854775808`（= 2⁶³，超出 SQLite 整数上限） | 空 | `课程不存在` | 1 |

依据：`get_course`（`core.py:259-279`）先做范围判断再查 `courses` 表，两种情况都
返回 `None`；CLI 在 `__main__.py:180-182` 打印常量 `ERR_NOT_FOUND`（`core.py:10`）
并 `return 1`。**实测**两项与上表逐项一致，stderr 中均无 `Traceback`；26 个 9
（`99999999999999999999999999`）实测同为「课程不存在」、退出码 1。测试覆盖：
未知编号 `tests/test_cli_flow.py:198-200`；2⁶³ 与 26 个 9 及带正号/前导零/外围空白
的越界形式 `:263-285`（其中 `:268` 显式断言 stderr 不含 `Traceback`）；
恰为 int64 上限的 `9223372036854775807` 按普通未知正整数处理（`:271-274`，实测
同为退出码 1「课程不存在」）。

### 5.3 失败时不新增课程或章节记录

- `get-course` 全程只有 `SELECT`（`core.py:267-278`），无论命中与否都不执行
  `INSERT`/`UPDATE`，因此 5.1、5.2 的失败都不会新增任何 `courses`/`chapters` 行。
- **实测**：对含样例课程的库连续执行 2⁶³、26 个 9 的失败查询后，再登记一门新课程，
  新编号仍为 2（失败查询不消耗自增编号），且 `get-course 1` 内容不变——与测试
  `tests/test_cli_flow.py:287-311` 的断言一致。
- 「不新增记录」与「不创建数据库文件」是两件事，边界见第 7 节。

## 6. 勘误：旧说明的 `OverflowError` 描述不适用于当前源码

既有说明 `docs/课程登记与课程详情查询流程说明.md` 第 7.5 节表格末行称：超出 64 位
整数范围的编号（如 26 个 9）会在查询时抛出**未捕获**的
`OverflowError: Python int too large to convert to SQLite INTEGER`、打印
traceback、退出码 1。

**该旧描述不适用于当前源码**，依据如下：

1. 当前源码在存储层显式声明了 SQLite 64 位有符号整数边界（`core.py:31-33`）：

   ```python
   _SQLITE_INT64_MIN = -(2**63)
   _SQLITE_INT64_MAX = 2**63 - 1
   ```

2. `get_course` 进入后、执行任何 SQL **之前**先做范围守卫（`core.py:262-266`）：

   ```python
   """超出 SQLite 整数范围的编号不可能对应任何课程，直接返回 None，
   避免把 OverflowError 暴露给调用方。"""
   if not _SQLITE_INT64_MIN <= course_id <= _SQLITE_INT64_MAX:
       return None
   ```

   越界编号在此即返回 `None`，`core.py:267-269` 的参数化查询根本不会执行，
   Python 大整数不会被绑定到 SQLite，`OverflowError` 无从产生。

3. CLI 把这个 `None` 与「库中无此行」一视同仁（`__main__.py:179-182`）：stderr
   输出 `课程不存在`，stdout 为空，退出码 1，无 traceback。

**实际结果（实测）**：`get-course 9223372036854775808` 与 26 个 9 均返回
stderr「课程不存在」、退出码 1、无异常堆栈；带外围形式的
` +9223372036854775808 `、`009223372036854775808` 因第 4 节的解析规则先被还原为
同一个越界整数，结果相同。直接调用函数级入口同样返回 `None`：
`get_course(conn, 2**63)`、`get_course(conn, int("9"*26))`、
`get_course(conn, -(2**63)-1)` 均为 `None`（测试
`tests/test_cli_flow.py:314-329`）。

因此：旧文档中那条「实测」声明只反映它撰写时的旧版行为（当时查询前没有范围守卫）；
对当前提交 `d3caa9e` 的源码与实测而言，**越界编号的确定结果是「课程不存在 / 退出码
1 / 无堆栈」**。本文不改动旧文档原文，仅在此明确其不再适用。

## 7. 「不新增记录」与「不创建文件」的边界

- **数据行层面**：查询不写入（见 5.3），任何 `get-course` 调用都不新增课程或章节
  记录。
- **文件/表结构层面**：`connect()` 先于编号解析与课程查找执行（`__main__.py:109`
  先于 `:129` 与 `:179`；`core.py:36-40` 的 `sqlite3.connect` 会创建不存在的文件，
  `executescript(_SCHEMA)` 以 `CREATE TABLE IF NOT EXISTS` 确保
  `courses`、`chapters` 表存在，`AUTOINCREMENT` 还会带来 `sqlite_sequence` 表）。
  所以**父目录已存在而数据库文件尚不存在**时，对未知课程的查询会**先建库建表，
  再返回「课程不存在」**。
- **实测**：在一个空目录中首次执行
  `python3 -m course_progress --db <新目录>/new.db get-course 7`，调用前该目录无
  `new.db`；调用后退出码 1、stdout 空、stderr「课程不存在」，且文件已创建，库中含
  `courses`、`chapters`、`sqlite_sequence` 三张表，前两张均为 0 行。
  对全新路径执行格式非法的 `get-course abc` 实测同样留下已建表的空库文件
  （退出码 2）——因为建库发生在格式判定之前。
- 父目录不存在时是另一种结果：`sqlite3.connect` 抛错，被
  `__main__.py:110-112` 捕获，stderr「无法打开数据库：unable to open database
  file」，退出码 1（README 第 7 行记载了父目录需预先存在）。
- 对已存在的库文件执行查询，无论成功失败，都不存在上述文件创建差异。

## 8. 既有语义与非目标

以下语义保持不变，本文仅记录、不修改：

- 章节顺序以登记时保存的 `position` 为准（第 3.3 节）；程序退出后重开同一 `--db`
  仍得相同顺序（第 3.4 节）。
