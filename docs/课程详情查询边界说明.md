# 课程详情查询（get-course）流程与边界说明

> 范围：仅覆盖 `get-course` 子命令——从公开入口 `python -m course_progress` 出发，
> 串起数据库定位、编号解析、课程查找、章节排序与 JSON 返回，以及各失败边界的确定结果。
> 登记入口 `add-course` 仅在为查询准备固定样例时出现，其完整流程见
> `docs/课程登记与课程详情查询流程说明.md`。
>
> 核对方式：
>
> - 源码版本：git 提交 `d3caa9e`（工作区干净）；
> - 实测环境：Python 3.14.4 / Linux，以 `python3 -m course_progress ...` 运行
>   （README 写作 `python`，除解释器名外命令形式一致）；
> - 本文结论分两类标注：**【实测】** 为本次在独立临时数据库中实际执行所得；
>   **【源码推导】** 为仅依据源码得出、未单独执行。文中不沿用旧文档的实测声明。
> - 实测在临时目录的独立数据库中完成，未改动仓库内 `data/course.db` 及任何源码。

## 3. 固定样例：Python 入门（安装环境 / 第一段程序）

以下命令在仓库根目录执行，使用一个全新的数据库文件（父目录 `data/` 需已存在，
`mkdir -p data` 即可）。登记走既有公开入口 `add-course`，本说明不新增任何参数。

### 3.1 建立样例（登记命令）

```bash
python -m course_progress --db data/course.db add-course \
    --title "Python 入门" --chapter "安装环境" --chapter "第一段程序"
```

- **【实测】** 在全新数据库上执行：标准输出 `{"course_id": 1}`，标准错误为空，退出码 0。
- 编号 1 的由来【源码推导】：`courses.id` 为 `INTEGER PRIMARY KEY AUTOINCREMENT`
  （`core.py:13-17` 的 `_SCHEMA`），编号由 SQLite 自动产生；`add_course` 用
  `cursor.lastrowid` 取回（`core.py:58-59`）。全新数据库的第一门课必得编号 1，
  之后单调递增。一般流程不应预设具体数字，应解析该 JSON 的 `course_id` 字段。

### 3.2 查询样例

```bash
python -m course_progress --db data/course.db get-course 1
```

预期结果（**【实测】**，在 3.1 的独立数据库上执行）：

- 标准输出：一行 JSON，内容为
  `{"course_id":1,"title":"Python 入门","chapters":["安装环境","第一段程序"]}`
  （JSON 内容如此；实际字节采用 `json.dumps` 默认分隔符，即冒号、逗号后各有一个空格，
  行尾一个换行符，`ensure_ascii=False` 中文不转义——`__main__.py:183`）。
- 标准错误：为空。
- 退出码：0。

### 3.3 章节为什么按保存的位置读取

- 写入侧【源码推导】：`add_course` 用 `enumerate(names)` 把 `--chapter` 的出现顺序
  落成 `position` 0、1（`core.py:60-63`），与课程行在同一事务内提交。
- 读取侧【源码推导】：`get_course` 以
  `SELECT name FROM chapters WHERE course_id = ? ORDER BY position`
  取章节名（`core.py:272-278`）。顺序由 `position` 列升序决定，与章节名字典序、
  行的物理顺序无关，因此读回顺序恒等于保存时的位置顺序。
- 联合主键 `(course_id, position)`（`core.py:18-23`）保证同一课程内位置唯一，
  排序结果确定。

### 3.4 程序退出后再次查询为何仍是相同顺序

- 数据写入普通 SQLite 文件并已提交（`add_course` 的 `with conn:` 事务，
  `core.py:57-63`），不依赖进程内存。
- **【实测】** 登记进程退出后，另起进程对同一 `--db` 路径执行 `get-course 1`，
  标准输出与 3.2 完全相同（`{"course_id":1,"title":"Python 入门","chapters":["安装环境","第一段程序"]}`，
  同样为默认分隔符的实际字节），退出码 0。
- 结论：只要 `--db` 指向同一路径且文件未被外部删除/移动，重复查询结果一致；
  顺序由每次查询的 `ORDER BY position` 重新计算，不依赖任何缓存或偶然行序。

### 3.5 保留的既有语义（本说明不引入任何变更）

- 标题与章节名在登记时去除首尾空白，但**保留内部空白与大小写**；查询原样返回
  数据库中保存的值（`core.py:49-50` 写入侧，`core.py:279` 读取侧无任何再加工）。
- 不同的 `--db` 文件中的课程彼此独立，互不可见（`README.md` 末行；代码中无任何
  跨文件共享逻辑）。
- 本说明未新增查询参数，也未新增输出字段：返回结构仍为
  `{"course_id", "title", "chapters"}` 三个字段（`core.py:279`）。

## 4. 失败情形：确定结果

以下每行均为 **【实测】**（在含 3.1 样例课程的独立数据库上执行；
「未知正整数」与「全新空库」两种库状态分别验证，结果相同）。

| 输入（get-course 的位置参数） | 标准输出 | 标准错误 | 退出码 | 源码依据 |
| --- | --- | --- | --- | --- |
| `0` | 空 | `课程编号必须为正整数` | 2 | `parse_positive_int` 要求 `> 0`（`__main__.py:99`），报错于 `__main__.py:130-132` |
| `-3` | 空 | `课程编号必须为正整数` | 2 | 正则允许负号但 `> 0` 拒绝（`__main__.py:23,99`） |
| `abc` | 空 | `课程编号必须为正整数` | 2 | 正则 `[+-]?\d+` 整体匹配失败（`__main__.py:23,96-97`） |
| 未知正整数（如 `42`） | 空 | `课程不存在` | 1 | `get_course` 查 `courses` 无此行返回 `None`（`core.py:267-271`），报错于 `__main__.py:180-182` |
| `9223372036854775808`（2^63） | 空 | `课程不存在` | 1 | 超出 SQLite 64 位整数范围，`get_course` 直接返回 `None`（`core.py:265-266`） |

共同特征【源码推导 + 实测确认】：失败时标准输出一律为空；两种情况都只打印一行
中文消息到标准错误，**不出现 Python 异常堆栈**——`main()` 对查询路径没有未捕获
异常（编号范围检查在 SQL 执行之前完成，见第 5 节）。

### 编号解析的接受规则（实测确认）

- 外围空白：`" 1 "` 按 1 处理（`raw.strip()`，`__main__.py:95`）——实测返回样例课程，退出码 0。
- 前导零：`007` 按 7 处理（`int("007") == 7`，`__main__.py:98`）——实测编号合法，
  但课程 7 不存在，报 `课程不存在`，退出码 1。
- 正号：`+1` 按 1 处理（正则允许可选正负号，`__main__.py:23`）——实测返回样例课程，
  退出码 0；`+3` 则合法但不存在，报 `课程不存在`，退出码 1。
- 注意区分：**编号合法只表示通过了解析，并不表示课程存在**。合法但未登记的编号
  一律走「课程不存在」、退出码 1，与编号格式错误（退出码 2）是两类不同结果。

## 5. 对旧文档 OverflowError 描述的更正

旧说明 `docs/课程登记与课程详情查询流程说明.md` 第 7.5 节称：超出 64 位整数范围的
编号「查询时抛未捕获 `OverflowError`，打印 traceback、退出码 1」。

**该描述不适用于当前源码。** 当前 `get_course()` 在执行任何 SQL 之前先做范围检查
（`course_progress/core.py:265-266`）：

```python
if not _SQLITE_INT64_MIN <= course_id <= _SQLITE_INT64_MAX:
    return None
```

（常量定义于 `core.py:32-33`，注释说明「超出该范围的编号不可能存在于库中」。）
因此超范围编号与「查无此行」走同一路径：返回 `None` → CLI 打印 `课程不存在`、
退出码 1（`__main__.py:180-182`），`OverflowError` 根本没有机会触发。

**【实测】** `get-course 9223372036854775808`：标准输出为空，标准错误为
`课程不存在`，退出码 1，无任何异常堆栈——与第 4 节表格一致。

## 6. 「不新增记录」与「不创建数据库文件」的区分

- **查询不新增任何课程或章节记录**【源码推导】：`get_course` 只执行两条 `SELECT`
  （`core.py:267-278`），无任何 INSERT/UPDATE；`main()` 的 `with conn:`（`__main__.py:113`）
  对只读路径没有可提交的写入。
- **但这不等于不创建数据库文件**【实测】：`connect(db_path)` 在编号解析与查询之前
  执行（`__main__.py:109` 先于 `:129`、`:179`），其内部 `sqlite3.connect()` 会在
  文件不存在时创建它，并执行 `_SCHEMA` 建表（`core.py:36-40`）。
- 因此，当**父目录已存在而数据库文件尚不存在**时，对一个未知课程执行
  `get-course` 的实际过程是：先创建数据库文件并建好 `courses`、`chapters`
  （以及 AUTOINCREMENT 附带的 `sqlite_sequence`）三张空表，再正常返回
  `课程不存在`、退出码 1。**【实测】** 在空的 `data/` 目录下执行
  `get-course 9` 后，`data/course.db` 出现，内含上述三张表且 `courses` 为 0 行。
- 推论：父目录不存在时连建库都失败，属另一条路径——stderr
  `无法打开数据库：…`、退出码 1（`__main__.py:110-112`），本条为源码推导，
  未在本说明范围内展开实测。
