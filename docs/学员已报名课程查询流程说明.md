# 学员已报名课程查询流程说明

> 范围：仅覆盖「按学员查询已报名课程」这一条路径——`list-learner-courses`
> 子命令从公开命令的参数输入到一行 JSON 输出之间的完整衔接：编号解析、
> 学员存在性检查、报名范围筛选、概览整理与命令行输出，并说明它与
> `list-courses`（全部课程概览）共用哪些读取规则。
>
> 本文只交付说明，不改变公开接口、JSON 字段、数据库表结构及其他命令的既有
> 行为；登记课程、登记学员与报名（`add-course`、`add-learner`、
> `enroll-learner`）只作为准备样例数据的既有入口被引用，其完整说明见
> README。
>
> 本文所有示例输出均标注为**预期结果**，含义是：按当前源码必然得到的结果，
> 且每条结论都在括号中给出可逐项核对的源码位置（文件与函数/行号）；仓库自带
> 测试 `tests/test_list_learner_courses.py`（14 个用例）对同一组行为做了回归
> 覆盖。
>
> 核对环境：
>
> - 源码版本：git 提交 `eda78e1`（撰写前工作区干净）；
> - Python 3.14.4 / Linux。README 命令写作 `python`，本机以等价的
>   `python3 -m course_progress ...` 核对，除解释器名外命令形式完全一致；
> - 核对均在临时独立目录的数据库上进行，未读取或改写仓库根目录既有的
>   `sample.db` 与 `data/course.db`；
> - `python3 -m unittest tests.test_list_learner_courses` 共 14 个用例，

## 2. 公开命令与参数

命令形式（`__main__.py:165-173` 的 argparse 定义；README 第 133 行）：

```bash
python -m course_progress --db sample.db list-learner-courses 1
```

- 位置参数 `learner_id`：学员编号，语义为「正整数」，解析规则见第 7 节。
- `--db <文件>`：SQLite 数据库文件路径，**父目录需预先存在**；文件不存在时
  自动创建并建表（README 第 7 行；`core.py:86-90`）。
- `--db` 写在子命令前或后均可：全局 `--db` 定义于 `__main__.py:42`，
  子命令级 `--db` 定义于 `__main__.py:168-170`（`default=argparse.SUPPRESS`），
  两者 dest 同为 `db`，`main` 只经一次 `getattr(args, "db", None)`
  （`__main__.py:188`）取值。下列两条命令等价，**预期结果**相同：

  ```bash
  python -m course_progress --db sample.db list-learner-courses 1
  python -m course_progress list-learner-courses 1 --db sample.db
  ```

  测试 `tests/test_list_learner_courses.py:128-146`
  （`test_db_option_after_subcommand`）覆盖子命令后的写法。
- 未提供 `--db` 时：标准错误 `必须通过 --db 指定数据库文件`，退出码 2
  （`__main__.py:188-191`）；父目录不存在导致打不开数据库时：标准错误
  `无法打开数据库：…`，退出码 1（`__main__.py:192-196`）。这两种情况不属于
  本查询特有的编号错误，本文不再展开。

## 3. 端到端流程总览：从参数到 JSON

一次 `list-learner-courses` 调用的固定次序：

```
命令行参数
  └─ argparse 解析（build_parser）                     __main__.py:165-173
       │    缺少位置参数 learner_id 时由 argparse 拒绝：
       │    英文 usage 错误写 stderr，stdout 为空，退出码 2；
       │    此阶段在 connect 之前，不创建数据库文件
       └─ 检查 --db 是否提供                            __main__.py:188-191
            └─ connect(db_path)：打开/创建 SQLite 并建表  core.py:86-90
                 │    （先于一切编号校验，见第 8 节）
                 └─ parse_positive_int(args.learner_id)  __main__.py:296 → 177-183
                      │    strip → 正则 fullmatch → int → >0
                      ├─ None：stderr「学员编号必须为正整数」
                      │         stdout 空，退出码 2       __main__.py:297-299
                      └─ 正整数 n
                           └─ list_learner_courses(conn, n)
                                                          __main__.py:300
                                                          → core.py:536-554
                                ├─ 64 位整数范围守卫      core.py:545-546
                                ├─ SELECT 1 FROM learners WHERE id=?
                                │    不存在 → 返回 None   core.py:547-551
                                │      → stderr「学员不存在」，stdout 空，
                                │        退出码 1         __main__.py:301-303
                                └─ 存在 → _list_course_overviews(
                                      conn, _LEARNER_COURSES_SCOPE, (n,))
                                                          core.py:552-554
                                                          → core.py:64-83
                                      │  报名范围筛选 + 概览整理（第 5 节）
                                      └─ 列表（可能为空）
                           └─ stdout 一行 JSON：
                              {"learner_id": n, "courses": [...]}
                              标准错误为空，退出码 0       __main__.py:304-310
```

五个环节的衔接要点：

1. **编号解析**（`__main__.py:296`，函数 `parse_positive_int` 在
   `__main__.py:177-183`）只决定「编号格式是否为正整数」，不查数据库；
   非法即退出码 2。
2. **学员存在性检查**在 core 层 `list_learner_courses` 内完成
   （`core.py:547-551`，`SELECT 1 FROM learners WHERE id = ?`）：查不到返回
   `None`，CLI 据此退出码 1。这一步同时承担「未报名有效学员」与「不存在
   学员」的分流——见第 6 节。
3. **报名范围筛选**由 SQL 片段 `_LEARNER_COURSES_SCOPE` 提供
   （`core.py:56-61`）：以 `enrollments` 为起点，按参数化的
   `WHERE e.learner_id = ?` 只圈定本学员的报名行。
4. **概览整理**统一走 `_list_course_overviews`（`core.py:64-83`），输出
   `course_id`/`title`/`chapter_count`，按课程编号聚合、升序。
5. **命令行输出**只在上述全部成功后执行一次
   `print(json.dumps({"learner_id": learner_id, "courses": courses},
   ensure_ascii=False))`（`__main__.py:304-309`），退出码 0。

## 4. 固定样例：学员甲报名两门课程（先报课程 2，再报课程 1）

以下命令均为 README 已记载的现有公开入口。请在一个**父目录已存在的独立空
目录**中执行（或先删除该目录下既有的 `sample.db`），以保证课程与学员编号
都从 1 开始。

### 4.1 准备样例数据

```bash
# 课程 1：入门培训，两章
python -m course_progress --db sample.db add-course \
    --title "入门培训" --chapter "第一章" --chapter "第二章"
# 课程 2：进阶培训，一章
python -m course_progress --db sample.db add-course \
    --title "进阶培训" --chapter "总览"
# 学员 1：学员甲
python -m course_progress --db sample.db add-learner --name "学员甲"
# 报名顺序刻意为「先 2 后 1」
python -m course_progress --db sample.db enroll-learner 1 --course 2
python -m course_progress --db sample.db enroll-learner 1 --course 1
```

五条命令的**预期结果**（标准输出各一行 JSON，标准错误为空，退出码均为 0；
编号来自 AUTOINCREMENT 的首个值，见 `core.py:19-22,29-32` 与
`add_course`/`add_learner` 对 `lastrowid` 的返回，`core.py:108-114,413-416`）：

```json
{"course_id": 1}
{"course_id": 2}
{"learner_id": 1}
{"learner_id": 1, "course_id": 2}
{"learner_id": 1, "course_id": 1}
```

即：学员甲（编号 1）已报名课程 2「进阶培训」（一章）与课程 1「入门培训」
（两章），报名先后为 2 → 1。

### 4.2 查询及其完整预期结果

```bash
python -m course_progress --db sample.db list-learner-courses 1
```

**预期结果**：退出码 **0**，标准错误为空，标准输出为一行 JSON：

```json
{"learner_id": 1, "courses": [{"course_id": 1, "title": "入门培训", "chapter_count": 2}, {"course_id": 2, "title": "进阶培训", "chapter_count": 1}]}
```

- 顶层只含 `learner_id` 与 `courses` 两个字段（由 `__main__.py:304-308` 的
  字典字面量固定）；`learner_id` 回显解析后的整数（编号外围形式的还原见
  第 7 节）。
- `courses` 数组顺序为 **课程 1 在前、课程 2 在后**，与报名先后（先 2
  后 1）无关——排序由查询中的 `ORDER BY c.id` 决定（`core.py:76`），
  `enrollments` 表也没有任何记录报名时间的列（表结构见 `core.py:33-37`）。
- 两个章节数分别为 **2** 与 **1**，来自对章节行的 `COUNT(ch.position)`
  （`core.py:73`），与准备数据一致。
- 测试 `tests/test_list_learner_courses.py:89-126`
  （`test_fixed_acceptance_sample`）以完全相同的数据与断言覆盖本样例。

## 5. 与「全部课程概览」共用的读取规则

`list-learner-courses` 与 `list-courses`（`core.py:117-139`，CLI 分派在
`__main__.py:206-219`）共用同一个概览整理函数
`_list_course_overviews`（`core.py:64-83`）。两者的差异**仅在课程范围**，
即 FROM/WHERE 片段（源码注释见 `core.py:49-51`）：

| | 全部课程概览 `list_courses` | 学员已报名课程 `list_learner_courses` |
| --- | --- | --- |
| 范围片段 | `_ALL_COURSES_SCOPE`（`core.py:52-55`）：`FROM courses AS c LEFT JOIN chapters AS ch ON ch.course_id = c.id` | `_LEARNER_COURSES_SCOPE`（`core.py:56-61`）：`FROM enrollments AS e JOIN courses AS c ON c.id = e.course_id LEFT JOIN chapters AS ch ON ch.course_id = c.id WHERE e.learner_id = ?` |
| 调用点 | `core.py:134` | `core.py:552-554` |
| 标题筛选 | 在概览结果上做 Python 子串筛选（`core.py:135-138`） | 无此参数 |

共用规则（均在 `_list_course_overviews` 内，`core.py:71-83`）：

- **字段固定**：`SELECT c.id, c.title, COUNT(ch.position)`（`core.py:73`），
  整理为 `{"course_id", "title", "chapter_count"}`（`core.py:80-82`），不含
  章节名称，也没有学习完成状态字段。
- **LEFT JOIN 保证章节数为 0 的课程仍出现**：没有章节的课程
  `COUNT(ch.position)` 为 0（本系统课程至少一章，此写法保证两种概览行为
  一致）。
- **按课程编号聚合去重**：`GROUP BY c.id`（`core.py:75`）。课程与章节是
  一对多，JOIN 后一门课会展开成多行；聚合后每门课程在结果中至多一项。
- **按课程编号升序**：`ORDER BY c.id`（`core.py:76`），与写入顺序、报名
  顺序均无关。

因此本查询的每一项与 `list-courses` 中同编号课程的对应项**必然同标题、同
章节数、同字段形态**，不存在两套整理逻辑产生分歧的可能。

## 6. 「未报名的有效学员」与「不存在的学员」

这是本查询最重要的分流，二者退出码不同、输出形态不同，判定完全来自
`list_learner_courses`（`core.py:536-554`）的返回值约定：

| 情形 | core 返回值 | CLI 行为 | 依据 |
| --- | --- | --- | --- |
| 学员存在，尚未报名任何课程 | 空列表 `[]` | stdout `{"learner_id": n, "courses": []}`，退出码 **0** | `core.py:547-554`；`__main__.py:300-310` |
| 学员不存在（含超出 SQLite 64 位整数范围的编号） | `None` | stdout 空，stderr `学员不存在`，退出码 **1** | `core.py:545-551`；`__main__.py:301-303` |

在样例库中再登记一位尚未报名的学员（既有命令，仅用于演示）：

```bash
python -m course_progress --db sample.db add-learner --name "学员乙"
python -m course_progress --db sample.db list-learner-courses 2
```

**预期结果**：退出码 0，标准错误为空，标准输出：

```json
{"learner_id": 2, "courses": []}
```

要点：**空 `courses` 是成功结果**，说明学员存在、只是没有报名行；它与报错
退出互斥。测试 `tests/test_list_learner_courses.py:148-156`
（`test_empty_courses_for_learner_without_enrollments`）覆盖。

## 7. 编号解析与失败结果

### 7.1 正号、前导零与外围空白沿用既有语义

编号解析统一走 `parse_positive_int`（`__main__.py:177-183`），步骤固定：

1. `text = raw.strip()`（`__main__.py:179`）——剥去**外围**空白（空格、
   制表符、换行等），不处理内部空白；
2. 用 `_ID_PATTERN = re.compile(r"[+-]?\d+")`（`__main__.py:34`）对剥空白
   后的整段做 `fullmatch`（`__main__.py:180`）——可选一个正负号后接一位
   以上数字，整段必须完全匹配；
3. `int(text)`（`__main__.py:182`）——消化前导零；Python 整数任意精度，
   此处不会因数字过长抛出异常；
4. 仅当 `value > 0` 时接受，否则返回 `None`（`__main__.py:183`）。

因此下列写法都按学员 **1** 处理，在样例库上的**预期结果**与第 4.2 节完全
相同（退出码 0，输出中 `learner_id` 均为整数 1）：

```bash
python -m course_progress --db sample.db list-learner-courses +1
python -m course_progress --db sample.db list-learner-courses 01
python -m course_progress --db sample.db list-learner-courses " 1 "
python -m course_progress --db sample.db list-learner-courses "$(printf '\t1\n')"
```

测试 `tests/test_list_learner_courses.py:269-289`
（`test_id_affixes_follow_get_learner_semantics`）逐一覆盖。该语义与
`get-learner` 等命令共用同一个解析函数，并非本查询新增。

### 7.2 失败示例（同一查询入口）

以下示例全部通过 `list-learner-courses` 这一个入口执行；两类失败的共同特征
是**标准输出为空、不出现异常堆栈**（消息均由
`print(..., file=sys.stderr)` 打印，不存在未捕获异常）。

**第一类：编号不是正整数 → 标准错误 `学员编号必须为正整数`，退出码 2**

```bash
python -m course_progress --db sample.db list-learner-courses 0
python -m course_progress --db sample.db list-learner-courses -3
python -m course_progress --db sample.db list-learner-courses abc
python -m course_progress --db sample.db list-learner-courses ""
```

四个输入的**预期结果**一致：标准输出为空，标准错误为一行

```
学员编号必须为正整数
```

退出码 **2**。其中空字符串 `""` 是 argparse 可接收的位置参数值（空串照常
传入），在 `parse_positive_int` 中经 `strip()` 后为空、正则匹配失败而被拒。
依据：`__main__.py:296-299`，消息常量 `ERR_BAD_LEARNER_ID`（`core.py:16`）。
测试 `tests/test_list_learner_courses.py:307-315`
（`test_bad_learner_id_format`，含 `0`、`-3`、`abc`、`1.5`、`""`）覆盖。

**第二类：正整数但学员不存在 → 标准错误 `学员不存在`，退出码 1**

```bash
# 样例库中只有学员 1、2，编号 3 不存在
python -m course_progress --db sample.db list-learner-courses 3
# 2^63，超出 SQLite 64 位有符号整数上限 9223372036854775807
python -m course_progress --db sample.db list-learner-courses 9223372036854775808
```

**预期结果**一致：标准输出为空，标准错误为一行

```
学员不存在
```

退出码 **1**，无异常堆栈。依据：越界编号先被范围守卫拦截
（`core.py:545-546`，边界常量在 `core.py:46-47`），其余正整数在
`SELECT 1 FROM learners WHERE id = ?` 中查无此行（`core.py:547-551`）；
两种情况都返回 `None`，CLI 统一在 `__main__.py:301-303` 报错。测试
`tests/test_list_learner_courses.py:317-329`
（`test_unknown_learner`、`test_overflow_id_treated_as_unknown`）覆盖。

补充：完全省略位置参数（`list-learner-courses` 后不跟编号）由 argparse 在
解析阶段拒绝，退出码 2、标准输出为空、无堆栈；该阶段发生在
`connect` 之前，不会创建数据库文件。测试
`tests/test_list_learner_courses.py:331-335`
（`test_missing_argument_uses_argparse_error`）覆盖。

## 8. 结果数据的来源语义与只读边界

### 8.1 排序、去重与隔离

- **按课程编号升序，不受报名先后影响**：`ORDER BY c.id`（`core.py:76`）；
  第 4 节先报课程 2 再报课程 1，输出仍是 1、2。
- **同标题课程分别列出**：概览按 `c.id` 分组、排序（`core.py:75-76`），
  两门同名课程编号不同即各占一项，不因标题相同而合并。测试
  `tests/test_list_learner_courses.py:194-229`
  （`test_same_titles_and_names_distinguished_by_id`）覆盖。
- **重复报名不重复显示**：报名关系表 `enrollments` 以
  `(learner_id, course_id)` 为联合主键（`core.py:33-37`），报名写入使用
  `INSERT OR IGNORE`（`core.py:498-502`），同一编号组合至多一行；查询侧的
  `GROUP BY c.id`（`core.py:75`）再次保证每门课至多一项。测试
  `tests/test_list_learner_courses.py:158-167`
  （`test_duplicate_enrollment_appears_once`）覆盖。
- **其他学员的报名不能混入**：范围片段以参数化条件
  `WHERE e.learner_id = ?`（`core.py:60`，参数绑定在 `core.py:553`）限定，
  只读取本学员的报名行。测试
  `tests/test_list_learner_courses.py:169-192`
  （`test_other_learners_enrollments_do_not_mix_in`）覆盖。

### 8.2 标题与章节数取查询时的当前值，报名关系不变

概览 SQL 每次执行都实时 JOIN 当前的 `courses` 与 `chapters`
（`core.py:58-59,73`），不保存报名时的标题或章节数快照。因此：

- 课程改名（`rename-course`）后再次查询，显示**新标题**；
- 章节追加/删除（`append-chapter`、`remove-chapter` 等）后再次查询，
  `chapter_count` 随之增减；
- 这些变化只影响概览中读出来的标题与章节数，**`enrollments` 中的报名关系
  本身不变**，课程编号不变，该学员仍报着同一编号的课程。

测试 `tests/test_list_learner_courses.py:231-267`
（`test_output_uses_current_title_and_chapter_count`）覆盖改名、追加章节后
章节数变 3、再删章节后恢复为 2 的完整过程。

### 8.3 重新打开同一数据库仍可查到报名关系

每条 CLI 命令都是独立进程，`connect` 以
`sqlite3.connect(db_path)`（`core.py:88`）打开普通 SQLite 文件；报名在
`enroll_learner` 的 `with conn:` 事务中提交（`core.py:487-502`），进程退出
后已落盘。再次对同一 `--db` 路径执行查询，会重新读到相同的报名关系；
不同 `--db` 文件彼此独立（README 第 201 行）。第 4.2 节的测试
（`tests/test_list_learner_courses.py:123-126`）在新进程中重复查询并断言
两次输出完全相同。

### 8.4 查询是业务只读操作，不产生完成状态

- `list_learner_courses`（`core.py:536-554`）与
  `_list_course_overviews`（`core.py:64-83`）全程只执行 `SELECT`，没有
  `INSERT`/`UPDATE`/`DELETE`；不修改课程、学员或报名记录。
- 数据库中只有 `courses`、`chapters`、`learners`、`enrollments` 四张业务
  表（`core.py:18-38`），**没有学习进度或完成状态表**；输出字段也只有
  `course_id`、`title`、`chapter_count`（`core.py:80-82`），不含章节名称
  与任何完成状态。
- 测试 `tests/test_list_learner_courses.py:291-303`
  （`test_query_is_read_only`）连续查询（含对不存在学员的失败查询）后断言
  输出与学员名册均不变。

### 8.5 数据库文件首次创建与业务只读的区别

「查询对业务数据只读」与「数据库文件可能首次被创建」是两个层面，互不矛盾：

- **文件/表结构层面**：`main` 在任何编号解析之前先调用
  `connect(db_path)`（`__main__.py:193`，先于编号解析的
  `__main__.py:296`）。对父目录已存在、文件尚不存在的全新路径，
  `sqlite3.connect` 会创建空文件，`executescript(_SCHEMA)` 以
  `CREATE TABLE IF NOT EXISTS` 建立四张业务表（`core.py:88-89,18-38`），
  两张 AUTOINCREMENT 表还会带来 `sqlite_sequence` 表。
- 因此对全新路径执行本查询，**即使查询失败也会先留下已建表的空库**：
  - `list-learner-courses 1` 打在全新文件上 → 文件先被创建，随后报
    `学员不存在`、退出码 1；
  - `list-learner-courses abc` 打在全新文件上 → 文件同样先被创建，随后报
    `学员编号必须为正整数`、退出码 2。

  两种情况下业务表均为 0 行——创建文件与表是 `connect` 的副作用，不是本
  查询写入了业务数据。测试
  `tests/test_list_learner_courses.py:337-342`
  （`test_missing_db_file_auto_created_then_reports_unknown`）断言全新文件
  在查询后存在且报「学员不存在」。
- **唯一不接触文件的情形**是第 7.2 节补充的 argparse 阶段拒绝
  （位置参数缺失）：它发生在 `connect` 之前。
- 对已存在的库文件执行查询，无论成功或失败，都不存在上述文件创建差异。
