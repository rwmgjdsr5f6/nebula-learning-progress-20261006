## 2. 调用形式与 `--db` 语义

命令语法（`__main__.py:165-173`）：

```
python -m course_progress [--db <文件>] list-learner-courses <learner_id> [--db <文件>]
```

- `learner_id` 为必填位置参数，语义为「学员编号（正整数）」（`__main__.py:172`）。
- 每次用 `--db` 指定 SQLite 数据库文件，**父目录必须预先存在**；文件不存在时
  自动创建并建表（`README.md:7`；`core.py:86-90`）。
- **`--db` 写在子命令前后语义相同**：全局 `--db` 定义于 `__main__.py:42`，
  子命令级 `--db` 定义于 `__main__.py:168-170`（`default=argparse.SUPPRESS`），
  两者都汇入同一个 `args.db`，由 `main` 在 `__main__.py:188` 统一读取。
  回归测试 `test_db_option_after_subcommand`（`tests/test_list_learner_courses.py:128-146`）
  与测试助手 `run_cli(..., db_first=False)`（同文件第 23–38 行）覆盖子命令后的写法。
- 不提供 `--db` 时：标准错误 `必须通过 --db 指定数据库文件`，退出码 2，
  不接触数据库（`__main__.py:188-191`）。

## 4. 固定样例：学员甲报名两门课程（先报课程 2，再报课程 1）

### 4.1 准备样例数据

在仓库根目录（父目录即当前目录，已存在）使用一个独立的样例库 `sample.db`。
若该文件已存在且需保证编号从 1 开始，请先删除文件或换用新路径；以下命令
均为 README 已记载的现有命令：

```bash

    --chapter "第一章" --chapter "第二章"
python -m course_progress --db sample.db add-course --title "进阶培训" \
    --chapter "总览"
python -m course_progress --db sample.db add-learner --name "学员甲"
python -m course_progress --db sample.db enroll-learner 1 --course 2
python -m course_progress --db sample.db enroll-learner 1 --course 1
```

预期结果：五条命令标准输出依次为（每条退出码均为 0，标准错误为空）：

```json

```
```json

```
```json
{"learner_id": 1}
```
```json

```
```json

```

即：课程 1「入门培训」含两章（第一章、第二章），课程 2「进阶培训」含一章
（总览），学员 1「学员甲」；**报名顺序为先课程 2 后课程 1**。报名输出只回显


标准输出为一行 JSON（中文不转义）：


## 5. 一次查询从参数到 JSON 的五个环节

### 5.1 编号解析（CLI 层）

`parse_positive_int`（`__main__.py:177-183`）对位置参数做三步处理：

1. `raw.strip()` 去除外围空白（`__main__.py:179`）；
2. 用正则 `_ID_PATTERN = re.compile(r"[+-]?\d+")`（`__main__.py:34`）做
   `fullmatch`（`__main__.py:180`）；
3. `int(text)` 后仅当 `value > 0` 时返回该整数，否则返回 `None`
   （`__main__.py:182-183`）。

本查询在 `__main__.py:296` 调用它；返回 `None` 时输出
`学员编号必须为正整数`、退出码 2（`__main__.py:297-299`）。该函数与
`get-learner`、报名、课程各命令共用，因此正号、前导零、外围空白的语义天然
一致（详见第 8.2 节）。

### 5.2 学员存在性检查（core 层）

解析通过后，CLI 把整数交给 `list_learner_courses`（`__main__.py:300`）。
存在性检查在 core 层完成（`core.py:536-554`）：

1. 先判断编号是否落在 SQLite 64 位有符号整数范围内
   （`_SQLITE_INT64_MIN/_SQLITE_INT64_MAX`，`core.py:45-47`；检查在
   `core.py:545-546`），超出范围直接返回 `None`，避免把 `OverflowError`
   暴露给命令行；
2. 再执行 `SELECT 1 FROM learners WHERE id = ?`（`core.py:547-549`），
   查不到行即返回 `None`（`core.py:550-551`）。

CLI 只区分 `None` 与非 `None`（`__main__.py:301-303`）：`None` 对应
`学员不存在`、退出码 1。注意「学员存在但未报名」不返回 `None`——存在性通过
后函数一定返回一个列表（可能为空），这是第 4.5 节两类结果的代码根源。

### 5.3 报名范围筛选

学员存在时，以 `_LEARNER_COURSES_SCOPE`（`core.py:56-61`）规定查询范围：

```sql
FROM enrollments AS e
JOIN courses AS c ON c.id = e.course_id
LEFT JOIN chapters AS ch ON ch.course_id = c.id
WHERE e.learner_id = ?
```

- `WHERE e.learner_id = ?` 的参数在 `core.py:552-554` 绑定为当前学员编号，
  **其他学员的报名行不可能进入结果**（回归测试
  `test_other_learners_enrollments_do_not_mix_in`，
  `tests/test_list_learner_courses.py:169-192`）。
- `enrollments JOIN courses` 是内连接：只列出该学员**实际报名**的课程；
  未报名课程不会出现，学员没有任何报名行时结果集为空（空列表而非报错）。
- 报名关系来自 `enrollments` 表，其联合主键为
  `(learner_id, course_id)`（`core.py:33-37`），同一编号组合至多一行；报名
  命令还使用 `INSERT OR IGNORE`（`core.py:498-502`），重复报名不会产生第二条
  关系。

### 5.4 概览整理（与全部课程概览共用的读取规则）

范围确定后，读取与整理全部走同一个内部函数 `_list_course_overviews`
（`core.py:64-83`）：

```sql
SELECT c.id, c.title, COUNT(ch.position)
<scope_sql>
GROUP BY c.id
ORDER BY c.id
```

并把每行整理为 `{"course_id": ..., "title": ..., "chapter_count": ...}`
（`core.py:80-83`）。本查询与 `list-courses` 全部课程概览
（`core.py:117-139`，调用处在 `core.py:134`）**共用以下全部规则**，源码注释
在 `core.py:49-51` 明确说明两种概览的差异仅在课程范围：

| 共有规则 | 实现位置 | 含义 |
| --- | --- | --- |
| 只读取编号、标题、章节数三项 | `core.py:73` 的 `SELECT c.id, c.title, COUNT(ch.position)` | 不读章节名称，也没有任何学习完成状态列 |
| `LEFT JOIN chapters` | `core.py:54,59` | 以课程为基准关联章节；没有章节的课程章节数为 0（当前登记规则保证每课至少一章，但共有规则本身如此） |
| 按课程编号聚合去重 | `core.py:76` 的 `GROUP BY c.id` | 同标题课程编号不同则各自成组、分别列出；即使底层出现多行，同一课程也只出现一次 |
| 按课程编号升序 | `core.py:77` 的 `ORDER BY c.id` | 与报名先后、标题字典序均无关 |
| 字典字段结构 | `core.py:80-83` | 两个概览命令输出的单项结构完全一致 |

两个范围常量分别是 `_ALL_COURSES_SCOPE`（`core.py:52-55`，
`FROM courses AS c LEFT JOIN chapters …`）与 `_LEARNER_COURSES_SCOPE`
（`core.py:56-61`，上一节的报名范围）；它们都以课程表别名 `c` 关联章节表
别名 `ch`，所以同一段 SELECT/GROUP BY/ORDER BY 可以直接复用。

由此得到本查询的三条去重/区分语义：

- **重复报名不重复显示**：联合主键保证关系只有一行，`GROUP BY c.id` 再按
  课程聚合一次。回归测试 `test_duplicate_enrollment_appears_once`
  （`tests/test_list_learner_courses.py:158-167`）。
- **同标题课程分别列出**：分组与排序都只按编号，标题不作为身份。回归测试
  `test_same_titles_and_names_distinguished_by_id`
  （`tests/test_list_learner_courses.py:194-229`）同时验证了同标题课程、
  同名学员按编号区分。
- **其他学员的报名不混入**：只由第 5.3 节的 `WHERE e.learner_id = ?` 决定。

### 5.5 命令行输出（CLI 层）

`main` 用 `json.dumps({"learner_id": learner_id, "courses": courses},
ensure_ascii=False)` 输出一行 JSON（`__main__.py:304-309`），随后返回 0
（`__main__.py:310`），由 `sys.exit(main())` 转为进程退出码
（`__main__.py:395-396`）。`learner_id` 回显的是解析后的整数（如 `+1`、
`01` 都规范化为 `1`），`courses` 即第 5.4 节整理出的列表。

## 6. 结果内容的语义：当前数据、持久化与只读

- **标题与章节数取查询时的当前值**：概览 SQL 每次实时 JOIN `courses` 与
  `chapters`（`core.py:56-61,71-79`），不保存报名时的快照。因此课程改名
  （`rename-course`）或章节增删（`append-chapter`、`remove-chapter` 等）之后，
  **下一次查询的概览随之变化**；`enrollments` 中的报名关系本身不变，也不依赖
  课程标题。回归测试 `test_output_uses_current_title_and_chapter_count`
  （`tests/test_list_learner_courses.py:231-267`）依次验证改名后标题更新、
  追加章节后 `chapter_count` 变 3、删除章节后恢复为 2。
- **重新打开同一数据库仍能查询报名关系**：报名在写入事务中提交
  （`core.py:487-502`），查询进程只读文件；换进程、重新打开同一 `--db` 路径
  结果一致（见第 4.4 节）。不同 `--db` 文件彼此独立（`README.md:201`）。
- **不产生学习完成状态**：数据库只有 `courses`、`chapters`、`learners`、
  `enrollments` 四张业务表（`core.py:18-38`），`enrollments` 仅存两个编号；
  概览单项只有 `course_id/title/chapter_count`（`core.py:80-83`），没有进度、
  分数或结业字段。
- **查询是业务只读操作**：`list_learner_courses` 与 `_list_course_overviews`
  中只有 `SELECT`（`core.py:71-79,547-554`），没有 INSERT/UPDATE/DELETE；
  CLI 虽在 `with conn:` 中分派（`__main__.py:197`），但本分支无任何写入可提交，
  课程、学员、报名记录均不被修改。回归测试 `test_query_is_read_only`
  （`tests/test_list_learner_courses.py:291-303`）在连续查询后比对输出不变，
  并核对学员名册原样。

## 7. 数据库文件首次创建与业务只读的区别

这两件事发生在不同层面，不可混为一谈：

1. **文件/表结构层面：打开即可能创建**。`main` 在分派到任何子命令分支前先
   执行 `connect(db_path)`（`__main__.py:193`，先于第 296 行的编号解析）。
   `connect` 中的 `sqlite3.connect(db_path)` 在文件不存在时创建空文件，随后
   `executescript(_SCHEMA)` 以 `CREATE TABLE IF NOT EXISTS` 建立各表
   （`core.py:86-90`，DDL 文本 `core.py:18-38`）。因此，即使对一条**全新路径**
   执行失败的查询，也会留下已建表的数据库文件——例如全新库执行
   `list-learner-courses 1`，文件被创建，随后报告 `学员不存在`、退出码 1。
   回归测试 `test_missing_db_file_auto_created_then_reports_unknown`
   （`tests/test_list_learner_courses.py:337-342`）断言失败后文件确实存在。
2. **业务记录层面：查询零写入**。建表 DDL 之外，本查询不插入、不修改、不删除
   任何课程、学员或报名行（见第 6 节）；失败路径同样不触碰业务表。全新库查询
   失败后，各业务表均为 0 行。
3. 唯一连文件都不会创建的失败是 **argparse 阶段拒绝**：位置参数缺失时
   `parse_args` 直接退出（`__main__.py:186-187` 尚未返回，`connect` 未执行），
   英文 usage 错误写标准错误、退出码 2。回归测试
   `test_missing_argument_uses_argparse_error`
   （`tests/test_list_learner_courses.py:331-335`）覆盖。
4. 父目录不存在属于打开失败：标准错误 `无法打开数据库：…`，退出码 1
   （`__main__.py:192-196` 捕获 `sqlite3.Error`）；准备样例库时父目录（当前
   目录）已预先存在，不触发该情形。

## 8. 失败情形（仅限 `list-learner-courses` 同一查询入口）

### 8.1 两类失败的输入、消息与退出码

| 输入类别 | 示例输入 | 标准输出 | 标准错误 | 退出码 | 代码位置 |
| --- | --- | --- | --- | --- | --- |
| 编号不是正整数 | `0` | 空 | `学员编号必须为正整数` | **2** | `__main__.py:296-299`；常量 `core.py:16` |
| 编号不是正整数 | `-3`（负数） | 空 | `学员编号必须为正整数` | **2** | 同上 |
| 编号不是正整数 | `abc` | 空 | `学员编号必须为正整数` | **2** | 同上 |
| 编号不是正整数 | 空字符串 `""` | 空 | `学员编号必须为正整数` | **2** | `strip()` 后为空，正则不匹配，`__main__.py:179-181` |
| 正整数但学员不存在 | `999`（库中无此学员） | 空 | `学员不存在` | **1** | `core.py:547-551` 返回 `None` → `__main__.py:301-303`；常量 `core.py:15` |

两类失败的共同特征：

- **标准输出为空**（失败分支只向 stderr 打印消息，不输出 JSON）；
- **不出现异常堆栈**：两类情形分别由 `print(..., file=sys.stderr)` 与显式
  `return` 处理，不存在未捕获异常。回归测试统一以 `assert_failure` 断言
  stdout 为空、消息精确相等、stderr 不含 `Traceback`
  （`tests/test_list_learner_courses.py:49-53`）；格式类用例在
  `test_bad_learner_id_format`（第 307–315 行，含 `0`、`-3`、`abc`、`1.5`、
  空字符串），不存在类用例在 `test_unknown_learner`（第 317–321 行）与
  `test_overflow_id_treated_as_unknown`（第 323–329 行）。
- 检查顺序固定为「先编号格式（退出码 2），后学员存在性（退出码 1）」，
  与 `get-learner` 的失败结果完全一致（`README.md:199`）。

### 8.2 正号、前导零与外围空白：沿用既有编号解析语义

本查询不自定义解析规则，直接使用各命令共用的 `parse_positive_int`，因此
以下输入在样例库中均按学员编号 **1** 处理，预期结果与第 4.3 节相同
（退出码 0，标准错误为空）：

| 输入 | 解析结果 | 生效规则 |
| --- | --- | --- |
| `+1` | 1 | 正则允许可选符号位 `[+-]?`（`__main__.py:34`） |
| `01` | 1 | `int()` 忽略前导零（`__main__.py:182`） |
| `" 1 "` | 1 | `strip()` 去外围空白（`__main__.py:179`） |
| 制表符/换行包裹的 `1`（如 `"\t1\n"`） | 1 | 同上，`strip()` 覆盖所有首尾空白字符 |

回归测试 `test_id_affixes_follow_get_learner_semantics`
（`tests/test_list_learner_courses.py:269-289`）逐一断言上述输入返回
`learner_id` 为整数 1 且课程列表正确。注意规范化只影响解析，回显的
`learner_id` 是整数 1；而 `+0`、`-0` 这类解析为 0 的输入仍因 `> 0` 判断被拒
（`__main__.py:183`）。

## 9. 核对结论

- 本文第 4.3 节的成功 JSON、退出码 0、空标准错误、数组按课程编号升序
  （1 在前 2 在后）、章节数 2 与 1，分别对应 `__main__.py:295-310`、
  `core.py:536-554` 与 `core.py:64-83`，并由
  `tests/test_list_learner_courses.py:89-126` 锁定。
- 未报名有效学员返回空 `courses`、退出码 0（`core.py:552-554`），与不存在
  学员返回 `None`、退出码 1（`core.py:547-551` +
  `__main__.py:301-303`）的区分在源码中是两条互斥路径。
- 排序与报名先后无关、重复报名不重复显示、同标题课程分别列出、其他学员报名
  不混入，均由 `_LEARNER_COURSES_SCOPE` 的 `WHERE`、联合主键与
  `GROUP BY c.id ORDER BY c.id` 保证（`core.py:33-37,56-61,71-83`）。
- 标题与章节数取查询时当前值、报名关系跨重开保持、查询不产生完成状态且业务
  只读，见 `core.py:71-83,487-502,536-554` 与第 6 节所引测试。
- 数据库文件的首次创建发生在 `connect`（`core.py:86-90`，先于业务校验），
  与查询本身业务只读不矛盾；`--db` 写在子命令前后经同一 `args.db` 生效
  （`__main__.py:42,168-170,188`）。
- 错误消息、退出码、stdout 为空、无堆栈、正号/前导零/外围空白语义、
  `9223372036854775808` 按不存在处理，均与 `get-learner` 一致并由失败类测试
  覆盖（`tests/test_list_learner_courses.py:306-342`）。
- 本次交付仅新增本说明文档；公开命令与参数、JSON 字段、SQLite 表结构及其他
  命令的行为均未改动。
