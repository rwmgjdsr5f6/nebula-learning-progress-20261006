## 2. 端到端路径总览

```
命令行参数
  └─ argparse 解析（build_parser）                    __main__.py:150-155
     │    缺少位置参数 learner_id 或 --course 时由 argparse 拒绝：
     │    英文 usage 错误写 stderr，stdout 为空，退出码 2
     └─ 检查 --db 是否提供                             __main__.py:188-191
          └─ connect(db_path)：打开/创建 SQLite 并建表   core.py:86-90
               │    （先于一切校验，见第 6.3 节）
               └─ parse_positive_int(args.learner_id)  __main__.py:251
                    非法 → stderr 学员编号必须为正整数，退出码 2
               └─ parse_positive_int(args.course)      __main__.py:255
                    非法 → stderr 课程编号必须为正整数，退出码 2
               └─ get_learner(conn, learner_id)        __main__.py:259
                    不存在 → stderr 学员不存在，退出码 1
               └─ get_course(conn, course_id)          __main__.py:262
                    不存在 → stderr 课程不存在，退出码 1
               └─ unenroll_learner(conn, learner_id, course_id)   core.py:506-533
                    ├─ 编号范围检查（超出 SQLite 64 位整数按不存在）
                    ├─ 学员、课程存在性复查
                    └─ DELETE FROM enrollments WHERE learner_id=? AND course_id=?
               └─ stdout 输出 {"learner_id": N, "course_id": M}   __main__.py:266
```

调用形式与数据库定位沿用整体 CLI 约定（README 第 7 行）：

- 通过 `python -m course_progress` 调用，每次用 `--db` 指定数据库文件；
  **`--db` 写在子命令前后均可**——全局 `--db` 定义于 `__main__.py:42`，
  `unenroll-learner` 子命令级的 `--db` 定义于 `__main__.py:153`；测试
  `tests/test_unenroll_cli.py:222-234`（`test_db_option_after_subcommand`）
  覆盖子命令后的写法，本文第 3 节实测也验证了两种形式。
- **父目录必须预先存在**；数据库文件不存在时自动建库建表
  （`core.py:86-90` 的 `sqlite3.connect(db_path)` + `_SCHEMA` 建表脚本，
  表结构见 `core.py:18-38`）。父目录不存在时：stderr `无法打开数据库：unable to
  open database file`，退出码 1（`__main__.py:192-196` 对 `connect` 的
  `sqlite3.Error` 捕获）。
- 子命令语法（`__main__.py:150-155`）：

  ```
  unenroll-learner <learner_id> --course <course_id>
  ```

  `learner_id` 为位置参数；`--course` 为必填标志（`required=True`，
  `__main__.py:155`）。两者均为「正整数编号」语义，解析规则见第 5.1 节。

## 3. 固定样例：入门培训与两名学员

以下命令形式与 README 记载的公开入口一致。在仓库根目录执行，使用独立的
`sample.db`（父目录即当前目录，已存在；若 `sample.db` 已存在请先删除或换用
其他路径，以保证编号从 1 开始）。

### 3.1 建立前置数据

```bash
python -m course_progress --db sample.db add-course --title "入门培训" --chapter "准备"
python -m course_progress --db sample.db add-learner --name "学员甲"
python -m course_progress --db sample.db add-learner --name "学员乙"
python -m course_progress --db sample.db enroll-learner 1 --course 1
python -m course_progress --db sample.db enroll-learner 2 --course 1
```

实测标准输出依次为（每条退出码均为 0）：

```json
{"course_id": 1}
{"learner_id": 1}
{"learner_id": 2}
{"learner_id": 1, "course_id": 1}
{"learner_id": 2, "course_id": 1}
```

即：课程 1「入门培训」（含一章「准备」），学员 1「学员甲」、学员 2「学员乙」，
两人均已报名课程 1。

### 3.2 取消报名

```bash
python -m course_progress --db sample.db unenroll-learner 1 --course 1
```

实测：标准输出为一行 JSON，标准错误为空，退出码 0：

```json
{"learner_id": 1, "course_id": 1}
```

输出只含 `learner_id` 与 `course_id` 两个字段（由 `core.py:533` 的返回字典与
`__main__.py:266` 的 `json.dumps(..., ensure_ascii=False)` 决定），即回显本次
取消的编号组合，不含名册或课程信息。

### 3.3 取消后的两项查询

课程 1 的报名名册（只剩学员乙）：

```bash
python -m course_progress --db sample.db list-course-learners 1
```

实测标准输出（退出码 0）：

```json
{"course_id": 1, "learners": [{"learner_id": 2, "name": "学员乙"}]}
```

学员甲的已报名课程（空数组）：

```bash
python -m course_progress --db sample.db list-learner-courses 1
```

实测标准输出（退出码 0）：

```json
{"learner_id": 1, "courses": []}
```

### 3.4 持久化、幂等与可重新报名

- **重新打开同一数据库结果保持**：每条 CLI 命令都是独立进程，第 3.3 节的查询
  本身就是在取消之后重新打开同一 `sample.db` 的结果；实测再次执行
  `list-course-learners 1` 输出不变。依据：删除在 `with conn:` 事务中提交
  （`core.py:518-532`），测试 `tests/test_unenroll_cli.py:155-164`
  （`test_unenroll_persists_across_reopen`）覆盖。
- **重复取消幂等**：对同一编号组合再次执行 `unenroll-learner 1 --course 1`，
  实测仍输出 `{"learner_id": 1, "course_id": 1}`、标准错误为空、退出码 0。
  依据：`DELETE ... WHERE learner_id=? AND course_id=?`（`core.py:529-532`）
  对不存在的行不报错；测试 `test_repeat_unenroll_is_idempotent`
  （`tests/test_unenroll_cli.py:132-143`）覆盖。
- **取消从未报名的有效编号组合同样成功**：学员、课程均存在但无报名关系时
  （如实测中另建课程 2 后执行 `unenroll-learner 1 --course 2`），返回相同的
  编号组合 `{"learner_id": 1, "course_id": 2}`、退出码 0。测试
  `test_unenroll_without_prior_enroll_succeeds`
  （`tests/test_unenroll_cli.py:145-153`）覆盖。
- **取消后可重新报名**：实测取消后执行 `enroll-learner 1 --course 1` 成功，
  名册恢复为包含学员甲。测试 `test_reenroll_after_unenroll`
  （`tests/test_unenroll_cli.py:204-220`）覆盖。
- **只移除目标编号组合**：课程、学员及其他报名关系保持不变。实测取消
  学员甲对课程 1 的报名后，`get-course 1` 仍返回
  `{"course_id": 1, "title": "入门培训", "chapters": ["准备"]}`，
  `get-learner 1` 仍返回 `{"learner_id": 1, "name": "学员甲"}`；测试
  `test_unenroll_only_removes_target_pair` 与
  `test_unenroll_does_not_change_course_or_learner_records`
  （`tests/test_unenroll_cli.py:166-202`）分别覆盖「其他报名关系不变」与
  「课程、学员记录不变」。

## 4. 一次取消请求从输入到结果

对应函数：`course_progress/core.py:506-533` 的 `unenroll_learner`；
CLI 分派在 `course_progress/__main__.py:250-267`。

1. **参数接收（CLI 层，`build_parser`，`__main__.py:150-155`）**：位置参数
   `learner_id` 与必填标志 `--course` 均由 argparse 收集为字符串；缺失时由
   argparse 直接拒绝（见第 5.2 节），不进入任何业务逻辑。
2. **打开存储（先于校验）**：`main` 在分派之前先执行 `connect(db_path)`
   （`__main__.py:193`），即任何编号校验发生之前，数据库文件与各表就已经
   创建（若原本不存在）。这与失败后是否留下文件相关，见第 6.3 节。
3. **编号解析**：`parse_positive_int`（`__main__.py:177-183`）先 `strip()`
   去外围空白，再用正则 `_ID_PATTERN = re.compile(r"[+-]?\d+")`
   （`__main__.py:34`）做 `fullmatch`，然后 `int(text)`，仅当结果 `> 0`
   才接受，否则返回 `None`。先解析学员编号（`__main__.py:251`），再解析
   课程编号（`__main__.py:255`）。
4. **存在性检查（CLI 层）**：依次调用 `get_learner`（`__main__.py:259`，
   实现 `core.py:459-472`）与 `get_course`（`__main__.py:262`，实现
   `core.py:380-400`）；任一返回 `None` 即报错退出，不进入删除。
5. **移除报名关系（core 层）**：`unenroll_learner` 在 `with conn:` 事务中
   先复查编号范围（`core.py:514-517`，超出 SQLite 64 位有符号整数范围
   `_SQLITE_INT64_MIN.._SQLITE_INT64_MAX`，见 `core.py:46-47`，直接返回
   `None`），再复查学员、课程存在性（`core.py:519-528`），最后执行
   `DELETE FROM enrollments WHERE learner_id = ? AND course_id = ?`
   （`core.py:529-532`）。`enrollments` 表以 `(learner_id, course_id)` 为
   联合主键（`core.py:33-37`），故该 DELETE 至多影响一行，且只针对该编号
   组合。
6. **输出**：返回 `{"learner_id": ..., "course_id": ...}`（`core.py:533`），
   CLI 以一行 JSON 打到 stdout（`ensure_ascii=False`），退出码 0
   （`__main__.py:266-267`）。

如实注明：第 4 步的存在性检查在 CLI 层完成，第 5 步 core 层又复查了一次；
两层结论一致，重复检查对命令行可观察行为无影响。

## 5. 失败情形与错误顺序

### 5.1 编号解析语义（与既有命令一致）

`parse_positive_int`（`__main__.py:177-183`）的接受与拒绝：

| 输入 | 结果 | 依据 |
| --- | --- | --- |
| `+1`、`01`、` 1 `（含制表符、换行等外围空白） | 接受，按 1 处理 | 正则允许可选正负号，`strip()` 去外围空白，`int()` 忽略前导零；测试 `test_id_affixes_follow_existing_semantics`（`tests/test_unenroll_cli.py:236-254`）覆盖 |
| `0`、`-3`、`abc`、`1.5`、空字符串 | 拒绝，报编号格式错误 | 正则 fullmatch 或 `> 0` 判断失败 |
| `9223372036854775808`（超出 SQLite 64 位整数范围的正整数） | 解析通过，但按**不存在**处理 | `core.py:514-517` 与 `get_learner`/`get_course` 中的范围检查（`core.py:386,465`）；测试 `test_overflow_ids_treated_as_unknown`（`tests/test_unenroll_cli.py:319-327`）覆盖 |

### 5.2 参数缺失：argparse 层拒绝

缺少位置参数 `learner_id` 或缺少 `--course` 时，由 argparse 在解析阶段拒绝
（`__main__.py:150-155` 的定义；`main` 尚未开始执行）：标准输出为空，
标准错误为英文 usage 错误（如 `error: the following arguments are required:
--course`），退出码 **2**。此阶段不接触数据库文件之外的任何业务逻辑——
如实注明：`connect` 在 `parse_args` 之后（`__main__.py:187,193`），故
argparse 拒绝时连数据库文件都不会创建。测试
`test_missing_arguments_use_argparse_error`（`tests/test_unenroll_cli.py:275-283`）
覆盖。

### 5.3 参数齐全时的检查顺序

参数齐全时按固定顺序检查，**只报告首个错误**（`__main__.py:250-264`）：

| 顺序 | 检查 | 触发条件 | 标准错误 | 退出码 | 代码位置 |
| --- | --- | --- | --- | --- | --- |
| 1 | 学员编号格式 | 不是正整数（如 `0`、`-3`、`abc`、`1.5`、空字符串） | `学员编号必须为正整数` | 2 | `__main__.py:251-254`，消息常量 `core.py:16` |
| 2 | 课程编号格式 | 不是正整数 | `课程编号必须为正整数` | 2 | `__main__.py:255-258`，消息常量 `core.py:13` |
| 3 | 学员存在性 | 正整数但无此学员（含超出 SQLite 整数范围） | `学员不存在` | 1 | `__main__.py:259-261`，消息常量 `core.py:15` |
| 4 | 课程存在性 | 正整数但无此课程（含超出 SQLite 整数范围） | `课程不存在` | 1 | `__main__.py:262-264`，消息常量 `core.py:12` |

实测示例（数据库中已有学员 1 与课程 1）：

- `unenroll-learner abc --course xyz` → stderr `学员编号必须为正整数`，退出码 2
  （两个编号都非法时只报学员编号格式错误）；
- `unenroll-learner 2 --course 2` → stderr `学员不存在`，退出码 1
  （学员与课程都不存在时只报学员不存在）；
- `unenroll-learner 1 --course 2` → stderr `课程不存在`，退出码 1；
- `unenroll-learner 9223372036854775808 --course 1` → stderr `学员不存在`，退出码 1。

测试 `TestUnenrollFailures`（`tests/test_unenroll_cli.py:274-327`）逐条覆盖
上述顺序与消息。

### 5.4 失败的共同特征

上述所有校验失败（含 argparse 拒绝）均满足：

- **标准输出为空**；
- **不显示异常堆栈**——消息来自 `print(..., file=sys.stderr)` 与 argparse
  自身，不存在未捕获异常（测试 `assert_failure` 断言 stderr 中不含
  `Traceback`，`tests/test_unenroll_cli.py:47-51`）；
- **已有业务记录不变**——格式错误与存在性失败发生在任何 DELETE 之前
  （对比第 4 节步骤 3–5 的先后），课程、学员、报名关系均不被修改。测试
  `test_failure_leaves_enrollments_untouched`（`tests/test_unenroll_cli.py:329-340`）
  在一连串失败调用后验证名册保持原样。

## 6. 存储边界

### 6.1 数据落在哪里

报名关系只存储在 `enrollments` 表（`core.py:33-37`），联合主键
`(learner_id, course_id)` 保证同一编号组合至多一行。取消报名只删除该表中
匹配的一行；`courses`、`chapters`、`learners` 表不被触碰（`core.py:529-532`
是唯一的数据修改语句）。

### 6.2 不同数据库互不影响

存储位置唯一来源是 `--db` 参数，没有默认路径或环境变量回退；不同 `--db`
文件中的课程、学员与报名关系彼此独立。测试
`test_unenroll_isolated_between_db_files`（`tests/test_unenroll_cli.py:256-271`）
验证在另一个数据库中执行取消不影响本库的报名关系。

### 6.3 失败仍可能留下空数据库

`connect(db_path)` 先于一切编号校验执行（`__main__.py:193` 先于 `:251`），
而 `connect` 会建库建表（`core.py:86-90`）。因此对**全新路径**执行一次
校验失败的取消（如对空库执行 `unenroll-learner 1 --course 1`，报
`学员不存在`、退出码 1），仍会留下已建表的空数据库文件。实测：失败后该
文件存在，内含 `courses`、`chapters`、`learners`、`enrollments`、
`sqlite_sequence` 五张表，`enrollments` 为 0 行。即「失败不修改业务记录」
不等于「失败不创建数据库文件和表」。唯一不接触数据库的失败是第 5.2 节的
argparse 拒绝（发生在 `connect` 之前）。
