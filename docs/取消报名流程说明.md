## 2. 处理路径总览：从公开入口到结果输出

一条 `unenroll-learner` 命令在源码中的完整路径（行号对应当前提交）：

1. **参数解析**：`build_parser`（`__main__.py:37-174`）注册的子命令要求一个
   位置参数 `learner_id` 和必填选项 `--course`（`__main__.py:150-155`）。
   缺少任一者时由 argparse 直接拒绝：打印用法与错误信息到标准错误，退出码 2，
   不进入任何业务逻辑（此时连数据库连接都尚未打开——`main` 在
   `__main__.py:187` 解析参数成功后才继续）。
2. **打开数据库**：`main` 先检查 `--db` 是否给出（`__main__.py:188-191`，
   缺失时标准错误输出 `必须通过 --db 指定数据库文件`，退出码 2），再调用
   `connect(db_path)`（`__main__.py:193` → `core.py:86-90`）：打开（必要时
   创建）SQLite 文件并执行 `_SCHEMA` 建表脚本（`core.py:18-38`，含
   `enrollments` 表，主键为 `(learner_id, course_id)`）。父目录不存在时
   `sqlite3.connect` 抛错，由 `__main__.py:194-196` 捕获，标准错误输出
   `无法打开数据库：...`，退出码 1。
3. **编号解析**：分派到 `unenroll-learner` 分支（`__main__.py:250`）后，先
   用 `parse_positive_int` 解析学员编号（`:251`），失败输出
   `学员编号必须为正整数`（常量 `ERR_BAD_LEARNER_ID`，`core.py:16`）、退出码 2；
   再解析 `--course` 课程编号（`:255`），失败输出 `课程编号必须为正整数`
   （常量 `ERR_BAD_ID`，`core.py:13`）、退出码 2。解析规则见第 5 节。
4. **存在性检查**：依次调用 `get_learner`（`__main__.py:259`）与
   `get_course`（`:262`）。学员不存在输出 `学员不存在`
   （`ERR_LEARNER_NOT_FOUND`，`core.py:15`）、退出码 1；课程不存在输出
   `课程不存在`（`ERR_NOT_FOUND`，`core.py:12`）、退出码 1。两个检查都只
   读不写。
5. **移除报名关系**：调用 `unenroll_learner(conn, learner_id, course_id)`
   （`__main__.py:265` → `core.py:506-533`）。函数内部先做 int64 范围检查
   （`core.py:514-517`，超出范围的编号直接返回 `None`，按不存在处理），再
   复查学员与课程存在性（`:519-528`），最后执行
   `DELETE FROM enrollments WHERE learner_id = ? AND course_id = ?`
   （`:529-532`），在 `with conn:` 事务中提交。无论该行是否存在，DELETE 都
   正常完成，函数返回 `{"learner_id": learner_id, "course_id": course_id}`
   （`:533`）。
6. **结果输出**：CLI 把返回值用 `json.dumps(..., ensure_ascii=False)` 打印
   为一行 JSON 到标准输出（`__main__.py:266`），返回 0（`:267`），`main`
   的返回值经 `sys.exit` 成为进程退出码（`:396`）。

## 3. 调用形式与数据库定位

与报名、查询完全相同的约定（README 对整体 CLI 有记载，源码同样适用）：

- 通过 `python -m course_progress` 调用，每次用 `--db` 指定数据库文件。
- **`--db` 写在子命令前后均可**：全局 `--db` 定义于 `__main__.py:42`，
  `unenroll-learner` 子命令级的 `--db` 定义于 `__main__.py:153`；测试
  `tests/test_unenroll_cli.py:222-233`（`test_db_option_after_subcommand`）
  覆盖子命令后的写法，本文第 4 节的实测也验证了两种形式。
- **父目录必须预先存在**；数据库文件不存在时会自动建库建表
  （`core.py:86-90` 的 `sqlite3.connect(db_path)` + `_SCHEMA`）。父目录不
  存在时：标准错误 `无法打开数据库：unable to open database file`，退出码 1
  （`__main__.py:194-196`）。
- 子命令语法（`__main__.py:150-155`）：

  ```
  unenroll-learner <learner_id> --course <course_id>
  ```

  `learner_id` 为位置参数；`--course` 为必填选项（`required=True`，
  `__main__.py:155`）。

## 4. 固定样例：取消学员甲对课程 1 的报名

### 4.1 建立前置数据

在一个**空目录**中执行以下命令（或先删除已有的 `sample.db`），保证课程与
学员编号从 1 开始。前置数据为：课程 1「入门培训」（含一章「准备」），
学员 1「学员甲」、学员 2「学员乙」，两人均已报名课程 1：

```bash
python -m course_progress --db sample.db add-course --title "入门培训" --chapter "准备"
python -m course_progress --db sample.db add-learner --name "学员甲"
python -m course_progress --db sample.db add-learner --name "学员乙"
python -m course_progress --db sample.db enroll-learner 1 --course 1
python -m course_progress --db sample.db enroll-learner 2 --course 1
```

实测五条命令的标准输出依次为（退出码均为 0，标准错误均为空）：

```json
{"course_id": 1}
{"learner_id": 1}
{"learner_id": 2}
{"learner_id": 1, "course_id": 1}
{"learner_id": 2, "course_id": 1}
```

### 4.2 取消报名

```bash
python -m course_progress --db sample.db unenroll-learner 1 --course 1
```

实测结果：标准输出**仅一行** JSON，标准错误为空，退出码 **0**：

```json
{"learner_id":1,"course_id":1}
```

如实注明：`json.dumps` 默认分隔符使实际字节中冒号后带空格
（`{"learner_id": 1, "course_id": 1}`，`__main__.py:266`）；测试按解析后的
JSON 比较，不限定键序与空格（`tests/test_unenroll_cli.py:118-120`），即上面
两种书写是同一内容。`--db` 写在子命令后
（`unenroll-learner 1 --course 1 --db sample.db`）结果完全相同（实测，
对应测试 `test_db_option_after_subcommand`）。

### 4.3 取消后的两项查询

查询课程 1 的报名名册，只剩学员乙：

```bash
python -m course_progress --db sample.db list-course-learners 1
```

实测标准输出（退出码 0，标准错误为空）：

```json
{"course_id": 1, "learners": [{"learner_id": 2, "name": "学员乙"}]}
```

查询学员甲已报名的课程，为空数组：

```bash
python -m course_progress --db sample.db list-learner-courses 1
```

实测标准输出（退出码 0，标准错误为空）：

```json
{"learner_id": 1, "courses": []}
```

对应测试：`tests/test_unenroll_cli.py:108-130`（`test_acceptance_flow`）。

## 5. 编号解析规则

`parse_positive_int`（`__main__.py:177-183`）对学员编号与课程编号使用同一
套规则，与既有命令一致：

1. 先 `strip()` 去除首尾空白；
2. 再用正则 `[+-]?\d+`（`__main__.py:34`）做 `fullmatch`；
3. 仅接受解析后**大于 0** 的整数。

因此：

- **正号、前导零、外围空白均可接受**：`+1`、`01`、`" 1 "`、`"\t1\n"` 都解析
  为 1。实测 `unenroll-learner "+1" --course " 01 "` 成功取消学员 1 对课程 1
  的报名，输出 `{"learner_id": 1, "course_id": 1}`，退出码 0。对应测试
  `tests/test_unenroll_cli.py:236-254`（`test_id_affixes_follow_existing_semantics`）。
- `0`、负数、非数字（如 `abc`）、小数（如 `1.5`）、空字符串均解析失败，
  按格式错误处理（见第 7 节）。
- **超出 SQLite 整数范围的正整数按不存在处理**：SQLite 整数为 64 位有符号
  （`core.py:45-47`），`get_learner`/`get_course` 与 `unenroll_learner` 对
  超出范围的编号直接返回 `None`（`core.py:465-466`、`:386-387`、`:514-517`），
  因此 `9223372036854775808`（2⁶³）这类编号不报格式错误，而是报
  `学员不存在`/`课程不存在`，退出码 1（实测；对应测试
  `test_overflow_ids_treated_as_unknown`）。

## 6. 取消后的状态保证

以下结论均有源码依据与测试覆盖；标注「实测」的为本次撰写时真实执行。

- **重新打开同一数据库结果保持**：删除在 `with conn:` 事务中提交
  （`core.py:518,529-532`），落盘于普通 SQLite 文件；每条 CLI 命令都是独立
  进程，随后的查询即重新打开同一数据库。实测取消进程退出后另起
  `list-course-learners 1`，名册仍只剩学员乙。对应测试
  `test_unenroll_persists_across_reopen`（`:155-164`）。
- **重复取消幂等**：对同一编号组合再次取消仍成功，返回相同的
  `{"learner_id": 1, "course_id": 1}`，退出码 0——DELETE 命中 0 行不算错误
  （`core.py:529-533`）。实测连续两次取消学员 2 对课程 1 的报名（第二次把
  `--db` 写在子命令后），两次输出逐字节相同。对应测试
  `test_repeat_unenroll_is_idempotent`（`:132-143`）。
- **从未报名的有效编号组合同样成功**：学员与课程都存在但从无报名记录时，
  取消仍返回 `{"learner_id": 1, "course_id": 1}`，退出码 0，标准错误为空
  （实测）。对应测试 `test_unenroll_without_prior_enroll_succeeds`（`:145-153`）。
- **取消后可重新报名**：`enroll-learner` 使用 `INSERT OR IGNORE`
  （`core.py:498-502`），取消后重新报名同一组合成功，名册恢复。实测取消
  学员 1 后重新 `enroll-learner 1 --course 1`，名册恢复为
  `{"course_id": 1, "learners": [{"learner_id": 1, "name": "学员甲"}]}`。
  对应测试 `test_reenroll_after_unenroll`（`:204-220`）。
- **只移除目标编号组合**：DELETE 的 WHERE 子句同时限定 `learner_id` 与
  `course_id`（`core.py:529-532`），课程、学员记录及其他报名关系不变。
  测试 `test_unenroll_only_removes_target_pair`（`:166-186`）验证取消
  (1,1) 后 (1,2)、(2,1) 两条报名保持；
  `test_unenroll_does_not_change_course_or_learner_records`（`:188-201`）
  验证课程详情 `{"course_id": 1, "title": "入门培训", "chapters": ["准备"]}`
  与学员记录 `{"learner_id": 1, "name": "学员甲"}` 逐项不变。
- **不同数据库互不影响**：每条命令只操作 `--db` 指定的一个文件。测试
  `test_unenroll_isolated_between_db_files`（`:256-271`）验证在另一个
  数据库中取消不影响本库的报名关系。

## 7. 失败情形与错误顺序

所有失败情形共同的可观察结果（实测与测试一致）：

- **标准输出为空**；标准错误只有一行中文消息（argparse 拒绝时为用法与错误
  信息），**不显示异常堆栈**（测试 `tests/test_unenroll_cli.py:47-51` 的
  `assert_failure` 逐条断言空 stdout、唯一消息、无 `Traceback`）；
- **已有业务记录不变**：所有校验失败都发生在 `unenroll_learner` 的 DELETE
  之前（CLI 层校验在 `__main__.py:251-264`，先于 `:265` 的调用），测试
  `test_failure_leaves_enrollments_untouched`（`:329-340`）在一系列失败后
  验证报名关系原样保留。

### 7.1 缺少必填编号或 `--course`：argparse 拒绝，退出码 2

| 输入 | 结果 |
| --- | --- |
| `unenroll-learner 1`（缺 `--course`） | 标准错误输出用法与 `error: the following arguments are required: --course`，退出码 2，标准输出为空 |
| `unenroll-learner --course 1`（缺位置参数） | 标准错误输出用法与 `error: the following arguments are required: learner_id`，退出码 2，标准输出为空 |

源码依据：`learner_id` 为位置参数、`--course` 为 `required=True`
（`__main__.py:154-155`），缺失时 argparse 在 `main` 的业务逻辑之前退出
（`__main__.py:187`）。对应测试 `test_missing_arguments_use_argparse_error`
（`:275-283`）。

### 7.2 参数齐全时的检查顺序：只报告首个错误

参数齐全时依次检查 **学员编号格式 → 课程编号格式 → 学员存在性 → 课程
存在性**，任一失败即返回，只报告首个错误：

| 顺序 | 检查 | 标准错误 | 退出码 | 源码位置 |
| --- | --- | --- | --- | --- |
| 1 | 学员编号格式 | `学员编号必须为正整数` | 2 | `__main__.py:251-254` |
| 2 | 课程编号格式 | `课程编号必须为正整数` | 2 | `__main__.py:255-258` |
| 3 | 学员存在性 | `学员不存在` | 1 | `__main__.py:259-261` |
| 4 | 课程存在性 | `课程不存在` | 1 | `__main__.py:262-264` |

实测示例（前置数据同第 4 节）：

- `unenroll-learner abc --course 1`、`unenroll-learner 0 --course 1` →
  `学员编号必须为正整数`，退出码 2；
- `unenroll-learner 1 --course xyz` → `课程编号必须为正整数`，退出码 2；
- `unenroll-learner abc --course xyz`（两个编号都非法）→ 只报
  `学员编号必须为正整数`，退出码 2；
- `unenroll-learner 3 --course 1` → `学员不存在`，退出码 1；
- `unenroll-learner 3 --course 9`（学员与课程都不存在）→ 只报
  `学员不存在`，退出码 1；
- `unenroll-learner 1 --course 9` → `课程不存在`，退出码 1；
- `unenroll-learner 9223372036854775808 --course 1` → `学员不存在`，
  退出码 1；`unenroll-learner 1 --course 9223372036854775808` →
  `课程不存在`，退出码 1。

对应测试：`test_bad_learner_id_format_reported_first`（`:285-292`）、
`test_bad_course_id_format_reported_after_learner_format`（`:294-305`）、
`test_unknown_learner_reported_before_unknown_course`（`:307-312`）、
`test_unknown_course`（`:314-317`）、`test_overflow_ids_treated_as_unknown`
（`:319-326`）。

## 8. 存储边界

- **数据行层面**：成功路径只删除 `enrollments` 表中目标编号组合的一行
  （`core.py:529-532`），不触碰 `courses`、`learners`、`chapters` 表与其他
  报名行；所有失败路径在任何 DELETE 之前返回，不修改任何业务记录。
- **文件/表结构层面**：`connect()` 先于一切编号与存在性校验执行
  （`__main__.py:193` 在 `:251` 之前），因此对**全新路径**执行注定失败的
  取消（如实测对新文件 `fresh.db` 执行 `unenroll-learner 1 --course 1`，
  报 `学员不存在`、退出码 1）仍会留下已建表的空数据库——实测该文件含
  `courses`、`chapters`、`learners`、`enrollments`、`sqlite_sequence` 五张
  表，`enrollments` 为 0 行。即「不修改业务记录」不等于「不创建数据库文件
  和表」；对已存在的库文件执行失败的取消则无此区别。
- **数据库之间互相独立**：不同 `--db` 文件中的课程、学员与报名关系彼此
  不可见，一个库中的取消不影响其他库（测试
  `test_unenroll_isolated_between_db_files`）。
